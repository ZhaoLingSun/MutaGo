## 1. 总原则

1. **C++ 是唯一生产规则权威**。Python 是独立实现的慢速差分 oracle，只产生参考结果、预期事件或规范投影；它不产生生产权威事件，也不进入生产裁决路径。
2. Python 不得调用、链接、翻译或复用 C++ 状态转移、合法性、提子、PSK 或 settlement 代码。两者可以共享只含数据的已冻结规则描述符、Schema 和测试夹具。
3. 差异出现时不得预设任一实现自动正确。必须回到冻结规则规范，生成最小复现并由规范裁决修复错误实现。
4. 规则接受/拒绝、错误类别、占位、actor、phase、配额、账本、位置超级劫键（`PositionalSuperkoKey` / PSK）上下文、settlement 顺序、计分、终局和派生 legal mask 均做精确比较，不使用浮点容差。
5. 神经网络后端数值测试可以使用预先声明的逐 dtype 容差，但该容差不得传播到规则状态、动作 codec、mask、事件顺序或训练样本的离散字段。
6. 所有随机测试必须可复现：记录随机种子、生成器版本、完整测试描述符、固定的初始 PSK 第零项、代码提交、编译器、构建选项、平台和失败前缀。
7. 搜索键、PSK 键和 NN-cache key 必须作为三个语义域分别构造和测试。官方 PSK 键的语义字段只含黑白占位；其字节编码或哈希实现未冻结，不得据此加入额外语义字段。
8. `legalMask` 不是 `GameState` 字段。测试必须从相同精确状态分别调用权威派生器并比较 `[1445]` 结果；若测试缓存，必须验证缓存绑定确切状态修订并正确失效。
9. M0 的 Python 合同工具只校验受限 JSON profile、Schema、描述符、动作向量与跨制品不变量；它不是生产 C++ reducer，也不是独立完整 Python 规则 oracle，不能替代后续 GOLD、DIFF 或 GATE-RULE-1M。`canonicalize`/`hash` 只执行 profile 校验；descriptor `validate` 和 repository `check` 才执行关闭式 Schema 与适用不变量。

## 2. 两级硬门槛及顺序

MutaGo 使用两个不同目的、不同时间点的硬门槛，不得合并或倒置：

| 门槛 | 时点 | 最低内容 | 阻塞对象 |
|---|---|---|---|
| **GATE-RULE-1M：早期规则差分硬闸门** | C++ 规则核心和独立 Python oracle 完成后，任何搜索、生产协议或数据生产实现之前 | 核心黄金夹具、重放/撤销、ASan/UBSan、至少一百万候选原子行动的精确差分，零可复现语义差异 | 搜索集成、生产引擎协议、Gateway/Web 产品路径、自博弈与训练数据生产、模型接入规则环境 |
| **GATE-PROD：完整生产者、训练与发行准入门槛** | 搜索、协议、Gateway/Web、Model V19、Inputs V9 和 Training Schema V1 均完成后 | 仍然有效的 GATE-RULE-1M 证书，加上 SEARCH/IO/NN/E2E、恢复、D4、迁移、生产者身份和发行检查 | 正式训练池、可追认训练数据、release candidate、稳定 beta 和社区分发 |

Schema 设计、测试向量设计和只用于规则差分的直接 harness 可以在 GATE-RULE-1M 前完成；**生产搜索、生产 gameplay 协议、产品服务和任何自博弈/训练数据 producer 不得越过该早期闸门先行实现或产数**。后期 GATE-PROD 不能替代或推迟早期规则闸门。

## 3. 可执行夹具契约

### 3.1 每个语义夹具必须表达

M0 语义夹具的字段与物理 JSON 布局由 `conformance-fixture-v1.schema.json` 和它引用的关闭式源 Schema 冻结。后续生产事件、命令和快照 envelope 仍可独立版本化，但不得重新解释 M0 夹具语义。每个夹具必须完整表达：

- 精确测试描述符或受严格限制的 `descriptor: null` 公开绑定；null 只允许精确绑定 `mutago.collapse-go` / `0.1.0-draft` / `a21c67d7962b71a3a53b895de824dc6312502362de5341103c0265c2c81d0899` 以及官方 19×19、双方 `1/1/1` 配置；
- 棋盘尺寸、完整配额向量、阈值、贴目、计分、初始 actor，以及初始空盘占据为 PSK 历史第零项；
- 初始精确状态，或从声明的初始状态开始的完整事件前缀；
- 稳定、确定的逻辑事件序位，不使用墙钟或容器顺序决定 settlement；
- 待执行命令或 typed-action 序列；
- 每一步接受/拒绝结果及稳定错误类别；
- 每一步的黑白占位、actor、phase、原子行动数、PASS 连续数、pending Double、配额、账本和终局状态；
- 每个规则事件稳定闭包后的 PSK 追加、每个 settlement event pop、捕获/移除集合及 no-op；
- 由精确状态单独派生的 `[1445]` legal mask；
- 语义提交边界中的接受结果、事件或事件组、下一状态修订和已提交日志位置；
- 如适用，中国式面积分、贴目和最终胜负。

初始空盘占据固定为 PSK 历史第零项；初始化时它是历史中唯一条目。夹具、随机运行 manifest、C++ reducer 和独立 Python oracle 都必须明确验证该不变量，不得提供关闭它的公共规则开关。

### 3.2 差分规范投影

C++ 与 Python 对同一稳定前缀和同一候选原子行动至少比较：

1. 接受或拒绝及稳定错误类别；
2. 黑白占位与 stable source identities 的规范投影；
3. 当前 actor、phase、pending Double owner/linkage；
4. 原子行动数、阈值、PASS 连续数和触发状态；
5. 双方初始、剩余和已用配额；
6. 完整特殊事件账本、逻辑顺序、armed/tombstone/captured/settled disposition；
7. occupancy-only PSK 历史或严格语义等价的序列，包括每个玩家事件和每个 settlement pop 的稳定占位；
8. settlement 触发原因、全局 newest-to-oldest 顺序、每步 no-op/能力移除/同步提子/闭包和稳定轨迹；
9. 从精确状态派生的 legal mask；
10. 接受事件组、下一精确状态、下一修订和日志位置是否形成同一个语义提交；
11. MVP 禁用死子协商移除与争议协议、两个连续 PASS 后对当前稳定盘面的计分，以及认输、超时和终局语义；
12. 调试模式下按坐标规范化的群、气、Eightway 连接和 Immortal 保护状态。

内存地址、容器迭代顺序、实现私有群 ID、缓存命中、墙钟、线程调度和搜索统计不属于规则语义比较项。

### 3.3 M0 可执行合同门槛

M0 合同检查必须在任何后续规则实现开始前持续通过：

1. 五个 Draft 2020-12 源 Schema 可加载，本地 `$ref` 自包含且未知字段关闭；
2. 规范描述符通过 Schema 与跨字段不变量校验，并精确绑定公开三元组；
3. `canonicalization-v1.json` 的所有正例产生逐字节相同 UTF-8 和 SHA-256，所有重复键、浮点、非 ASCII、unsafe integer、非法 UTF-8、非法 JSON 与数字词法反例均被受限 profile 拒绝；profile 本身不判断 descriptor 字段；
4. `public-identity-v1.json` 精确得到 `14973` 字节和 `a21c67d7962b71a3a53b895de824dc6312502362de5341103c0265c2c81d0899`；
5. `descriptor-invalid-v1.json` 拒绝未知字段、错误公开 ID、错误初始 PSK、point-major 动作和启用 MVP 死子捷径等变体；
6. `action-v1.json` 覆盖全部动作族边界、PASS、9/13/19 居中、footprint 拒绝、canonical envelope 拒绝与八种 D4 往返；
7. 合同示例和 mismatch bundle 满足各自 Schema，身份、描述符、动作和语义投影引用一致。

仓库内快速入口为：

```bash
python3 tools/contract/contract.py check
python3 -m unittest discover -s tests/contracts -p 'test_*.py'
```

CLI 分层也属于门槛：`canonicalize FILE` 与 `hash FILE` 对任意 profile-valid JSON 成功不构成 descriptor 有效性证明；同一输入必须由 `validate ruleset-descriptor-v1 FILE` 执行关闭式 Schema 和描述符不变量，仓库整体由 `check` 执行固定 Schema、引用、描述符、向量、示例和跨制品绑定。

该门槛证明 M0 数据合同内部一致，不证明生产 C++ reducer、独立完整 Python oracle、搜索、NN、Gateway 或 Web 已实现或通过。

| CG-DBL-006 | Double 账本事件保留到 settlement；其 pop 为可见 no-op，仍产生稳定 PSK 追加，盘上 source stone 随后只按普通石处理。 |

### 5.6 位置超级劫

| ID | 场景与精确断言 |
|---|---|
| CG-PSK-001 | `PositionalSuperkoKey` 只比较黑白占位；actor、特殊标记、配额、行动号、phase 和账本差异不能使重复占位变合法。 |

### 5.7 Settlement

| ID | 场景与精确断言 |
|---|---|
| CG-SET-001 | 在阈值前连续两个 PASS 触发 settlement 而非直接计分；两次 PASS 都是原子玩家事件并计入行动数。 |
| CG-SET-002 | 达到 `T` 的行动先完成自己的全部规则事务、稳定提交和 PSK 追加，再以最新事件身份触发 settlement；不得在行动中途结算。 |
| CG-SET-003 | 双方全部已用特殊事件按唯一逻辑序位全局 newest-to-oldest 处理，不按颜色分组，不使用墙钟。 |
| CG-SET-004 | 一次只停用一个事件的能力；每步全盘重建并同步移除零气未保护群，必要时重复到确定性闭包；较新步骤结果可影响较旧步骤。 |

| CG-SET-006 | PSK 不拒绝任何 settlement 步骤；每个 event pop 的稳定结果都追加并约束之后的玩家行动，不稳定中间态不追加。 |

## 7. 撤销、重放、D4 与运行时检查

### 7.1 撤销、重做与检查点

- 对每个黄金夹具，在每个原子玩家行动前后执行撤销与重做，并比较完整规范投影。
- 必须覆盖 Double start 后的同方中间态、NORMAL/PASS continuation、`A=T-2`、第 `T` 个行动、settlement 前后、每个 settlement pop 的审计重放、post-settlement 普通行棋、MVP 两次 PASS 直接计分和终局。
- 撤销 settlement 必须恢复能力状态、配额消耗事实、完整账本、PASS 状态、PSK 和日志位置；重做产生相同逻辑顺序和稳定状态。
- 从任意合法检查点追加同一后缀的结果必须等于从初始状态完整重放；检查点不得丢失 PSK、账本或 pending Double。

### 7.2 D4 一致性

每个可变换黄金局面必须覆盖八种 D4：

- 占位、特殊锚点、动作、捕获集合、群、气和派生 legal mask 按同一坐标映射等变；
- 规则身份、行动数、配额、账本顺序、PASS 和胜负不因几何变换改变；
- policy、逐动作 Q、legal mask、T0/T1 policy targets 与 visit counts 分别置换四个 361 点动作块；ownership 及任何空间型 survival/辅助 target 按每通道单一 19×19 点置换变换；global、标量及非空间 target 不变。不得在 survival 精确张量形状仍为 **UNFROZEN** 时预先固定其 action 布局；
- settlement 步数、no-op 位置和事件逻辑顺序不变，仅坐标集合变换；
- symmetry 及其 inverse 后，所有离散工件逐 bit 恢复。

### 7.3 ASan、UBSan 与调试不变量

- 规则核心、日志重放、撤销/重做、全部核心黄金夹具及早期差分运行的指定分层必须分别在 ASan 与 UBSan 构建中通过且零报告。
- 禁止宽泛 suppression 隐藏项目代码问题；第三方 suppression 必须精确、带来源并证明不覆盖 MutaGo/KataGo 自有路径。
- 调试构建在每个稳定边界检查：群/气缓存可由全盘重建复现；事件序位唯一；配额只递减；PSK 追加未丢失；不稳定 settlement 中间态未进入 PSK；pending Double 只开放 NORMAL/PASS；提交的状态修订与日志位置一致。

## 8. GATE-RULE-1M：早期一百万原子行动规则差分硬闸门

### 8.1 计数单位

一个计数单位是：从完全相同、可重放的稳定状态向 C++ 和 Python 提交同一个候选原子行动，并完成第 3.2 节的全部规则投影比较。

- 点行动或 PASS 各计一个；Double start 与 continuation 分别计数。
- settlement 内部 event pop 不计作随机玩家候选，但其完整稳定轨迹和每次 PSK 追加在触发行动的比较中逐项相等。
- 若双方都拒绝，仍计作一个非法候选，且双方状态、修订和日志位置必须不变。
- 若双方都接受，只有语义提交边界和全部投影比较通过后，才从新稳定状态继续。

### 8.2 闸门前置条件

- C++ 规则 reducer 与 Python oracle 已分别实现冻结的规则语义；
- 核心 GOLD/PROP/UNDO/REPLAY/SAN 夹具通过；
- Action Schema V1 codec 已通过全部 1445 ID 测试；
- 初始空盘占据作为 PSK 历史第零项已经写入运行 manifest，并由两种实现的初始化投影共同验证；
- 运行中的每个配置分层都绑定其完整规范描述符、语义版本和 lowercase SHA-256。官方 19×19、双方 `1/1/1` 分层必须精确绑定 14973 字节公开描述符及 `mutago.collapse-go` / `0.1.0-draft` / `a21c67d7962b71a3a53b895de824dc6312502362de5341103c0265c2c81d0899`；9×9、13×13 或非官方配额分层必须内嵌各自完整描述符并使用各自摘要，不得复用官方身份。报告和不可变 manifest 必须逐分层记录并复核这些绑定；

### 8.3 合格运行范围

- 至少 `1,000,000` 个合法与非法候选原子行动，零可复现 C++/Python 语义差异。
- 覆盖 9×9、13×13、19×19；官方双方 `1/1/1`；以及包含 `0`、大于 `1` 和混合值的非官方完整配额向量。每一非官方尺寸或配额配置作为独立 descriptor/identity 分层计数和报告，不能被计入官方公开身份分层；
- 覆盖 NORMAL、IMMORTAL、DOUBLE_START、EIGHTWAY、PASS、NORMAL continuation、PASS continuation、配额耗尽、错误 phase 和终局后非法行动。
- 覆盖 `A=T-2`、`A=T-1`、第 `T` 个行动、阈值前双 PASS、settlement 前后、tombstone/no-op、PSK、普通自杀、Immortal 保护、Eightway 重建，以及 MVP 无死子捷径的两次 PASS 直接计分路径。
- 生成器以合法可达前缀为基础，并混入结构化非法候选；不得只使用某一个实现给出的“合法动作列表”来回避分歧。
- 具体采样权重、分层下限和种子清单为 **UNFROZEN**，但必须在运行开始前写入不可变 manifest，运行后不得为改善结果而修改。

### 8.4 失效与差异处理

合格计数必须发生在最后一次影响规则语义、C++ reducer、Python oracle、事件投影、PSK、settlement、动作 codec 或重放的修改之后，修复前后的计数不得相加。

发现差异时：

1. 立即保存测试描述符、初始 PSK 第零项投影、构建信息、种子、完整前缀、候选行动和双方投影；
2. 自动最小化为最短可复现前缀并生成永久回归夹具；
3. 依据规范裁决并修复错误实现，不得简单让 Python 模仿 C++；
4. 从零重新运行至少一百万候选；
5. 无法解释的偶发差异继续阻塞，只有证明为外部工具或硬件故障并完成干净重跑后才能排除。

### 8.5 闸门后才能开始的工作

只有 GATE-RULE-1M 通过后，才允许开始：

- Collapse Go 搜索与转置集成；
- 生产 C++ gameplay 协议、Gateway/WebSocket 和客户端产品路径；
- 自博弈、replay、训练样本或其他数据 producer；
- 把 Model V19 接入可产生训练数据的 Collapse 环境。

该闸门不依赖 SEARCH、NN 或 E2E 完成；把这些后期条件并入早期闸门会造成依赖倒置，属于不合格路线。

## English Summary

C++ is the sole production rules authority; Python is a separately implemented slow oracle that produces reference semantics, not production-authoritative events. Both implementations must compare exact acceptance, errors, occupancy, actor and phase, quotas, event-ledger state, occupancy-only positional-superko history, every stable settlement closure, derived 1445-bit legality, scoring, termination, and the semantic commit boundary. `legalMask` is derived from exact state and is never a `GameState` field.

M0 has a separate executable-contract gate. Five closed Draft 2020-12 source schemas, the canonical descriptor, canonicalization and identity vectors, invalid-descriptor variants, all action/D4 vectors, conformance examples, and mismatch bundles must pass `tools/contract/contract.py check` and the contract unit suite. `canonicalize` and `hash` validate only the restricted JSON profile; descriptor `validate` and repository `check` additionally enforce the closed descriptor schema and applicable invariants. This proves data-contract consistency only; it does not implement or validate the production reducer, the full independent Python oracle, search, neural integration, Gateway, or Web.

The frozen public identity is `mutago.collapse-go` / `0.1.0-draft` / descriptor SHA-256 `a21c67d7962b71a3a53b895de824dc6312502362de5341103c0265c2c81d0899`. The restricted profile rejects duplicate keys, floats, non-ASCII data, unsafe integers, invalid UTF-8, and invalid number syntax; it does not validate descriptor fields. The 14,973-byte descriptor separately passes the closed descriptor schema, which rejects unknown fields, invalid public bindings, incorrect PSK seeding, point-major action layouts, and enabled MVP dead-stone shortcuts. Internal variant IDs and repository slugs are not public identity.

Testing is deliberately split into two later implementation gates. **GATE-RULE-1M** occurs after independent C++ and Python rule implementations and before search, production gameplay protocol, Gateway/Web, self-play, or training-data production. It requires golden/replay/undo/sanitizer coverage and at least one million reproducible legal and illegal atomic-action comparisons with zero reproducible semantic differences. The later **GATE-PROD** retains a valid million-action certificate and adds search, protocol, persistence recovery, Model V19, Inputs V9, Training Schema V1, D4, migration, SGF, Gateway/Web, end-to-end authority, provenance, identity, and release checks.

Official Collapse Go uses occupancy-only positional superko. Initial empty occupancy is the sole history entry at initialization and has index zero. Every accepted rule event’s stable post-state is appended; an action that triggers settlement appends its stable closure first, then every newest-to-oldest event pop appends its stable closure. Tombstone/no-op steps may append duplicates, settlement repetitions are allowed, and unstable intermediates are excluded.

Action Schema V1 is kind-major: NORMAL `0..360`, IMMORTAL `361..721`, DOUBLE_START `722..1082`, EIGHTWAY `1083..1443`, and PASS `1444`, with `a=361*k+p`. Canonical Action V1 is a closed object containing exactly `schemaVersion`, `actionId`, and `kind`; coordinates are derived, and missing/unknown fields, unknown versions, redundant coordinates, and inconsistent `kind`/ID pairs fail closed. The 9x9, 13x13, and 19x19 footprints use centered offsets `(5,5)`, `(3,3)`, and `(0,0)`.

The MVP enables neither agreed dead-stone removal nor a dead-stone dispute protocol. Ordinary play continues until two consecutive passes and then scores the current stable board. Administrative termination is accepted only at exposed stable boundaries: termination-first yields one immediate terminal event with no candidate action, settlement, or score; action-first requires any triggered settlement to complete atomically before a later termination is considered. Operational timeouts and cancellation never synthesize game `TIMEOUT`. Any future negotiation flow requires a new semantic version, descriptor, and tests. Remaining open work covers production schemas, persistence mechanics, physical key integration, and SGF properties, not public identity, initial PSK seeding, Action V1, or the current dead-stone policy.
