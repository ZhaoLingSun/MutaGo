> **上游基线**：KataGo stable v1.16.5，提交 `ba938676d7f42d70950b3a535af2466fb642008c`

本文使用：

- **FROZEN**：必须满足的测试语义、门槛、顺序或架构边界。
- **UNFROZEN**：测试载体、字段、采样权重、持久化或工程参数尚未冻结。
- **AUDIT-BLOCKED**：必须先取得上游源码、模型、格式或独立规范化证据，才能写出正确断言。

## 1. 总原则

1. **C++ 是唯一生产规则权威**。Python 是独立实现的慢速差分 oracle，只产生参考结果、预期事件或规范投影；它不产生生产权威事件，也不进入生产裁决路径。
2. Python 不得调用、链接、翻译或复用 C++ 状态转移、合法性、提子、PSK 或 settlement 代码。两者可以共享只含数据的已冻结规则描述符、Schema 和测试夹具。
3. 差异出现时不得预设任一实现自动正确。必须回到冻结规则规范，生成最小复现并由规范裁决修复错误实现。
4. 规则接受/拒绝、错误类别、占位、actor、phase、配额、账本、位置超级劫键（`PositionalSuperkoKey` / PSK）上下文、settlement 顺序、计分、终局和派生 legal mask 均做精确比较，不使用浮点容差。
5. 神经网络后端数值测试可以使用预先声明的逐 dtype 容差，但该容差不得传播到规则状态、动作 codec、mask、事件顺序或训练样本的离散字段。
6. 所有随机测试必须可复现：记录随机种子、生成器版本、完整测试描述符、初始 PSK 播种策略、代码提交、编译器、构建选项、平台和失败前缀。
7. 搜索键、PSK 键和 NN-cache key 必须作为三个语义域分别构造和测试。官方 PSK 键的语义字段只含黑白占位；其字节编码或哈希实现未冻结，不得据此加入额外语义字段。
8. `legalMask` 不是 `GameState` 字段。测试必须从相同精确状态分别调用权威派生器并比较 `[1445]` 结果；若测试缓存，必须验证缓存绑定确切状态修订并正确失效。

## 2. 两级硬门槛及顺序

MutaGo 使用两个不同目的、不同时间点的硬门槛，不得合并或倒置：

| 门槛 | 时点 | 最低内容 | 阻塞对象 |
|---|---|---|---|
| **GATE-RULE-1M：早期规则差分硬闸门** | C++ 规则核心和独立 Python oracle 完成后，任何搜索、生产协议或数据生产实现之前 | 核心黄金夹具、重放/撤销、ASan/UBSan、至少一百万候选原子行动的精确差分，零可复现语义差异 | 搜索集成、生产引擎协议、Gateway/Web 产品路径、自博弈与训练数据生产、模型接入规则环境 |
| **GATE-PROD：完整生产者、训练与发行准入门槛** | 搜索、协议、Gateway/Web、Model V19、Inputs V9 和 Training Schema V1 均完成后 | 仍然有效的 GATE-RULE-1M 证书，加上 SEARCH/IO/NN/E2E、恢复、D4、迁移、生产者身份和发行检查 | 正式训练池、可追认训练数据、release candidate、稳定 beta 和社区分发 |

Schema 设计、测试向量设计和只用于规则差分的直接 harness 可以在 GATE-RULE-1M 前完成；**生产搜索、生产 gameplay 协议、产品服务和任何自博弈/训练数据 producer 不得越过该早期闸门先行实现或产数**。后期 GATE-PROD 不能替代或推迟早期规则闸门。

## 3. 可执行夹具契约

### 3.1 每个语义夹具必须表达

字段名和物理 JSON 布局为 **UNFROZEN**，但每个夹具必须完整表达：

- 精确测试描述符及其非公共状态；在公共身份分配前，`rulesetId`、规范描述符和公开哈希必须明确标为 `unassigned`，不得伪造最终值；
- 棋盘尺寸、完整配额向量、阈值、贴目、计分、初始 actor 和初始 PSK 播种策略；
- 初始精确状态，或从声明的初始状态开始的完整事件前缀；
- 稳定、确定的逻辑事件序位，不使用墙钟或容器顺序决定 settlement；
- 待执行命令或 typed-action 序列；
- 每一步接受/拒绝结果及稳定错误类别；
- 每一步的黑白占位、actor、phase、原子行动数、PASS 连续数、pending Double、配额、账本和终局状态；
- 每个规则事件稳定闭包后的 PSK 追加、每个 settlement event pop、捕获/移除集合及 no-op；
- 由精确状态单独派生的 `[1445]` legal mask；
- 语义提交边界中的接受结果、事件或事件组、下一状态修订和已提交日志位置；
- 如适用，中国式面积分、贴目和最终胜负。

初始空盘是否播种为 PSK 历史第零项目前是 **UNFROZEN**。在该项冻结前，每个夹具和随机运行 manifest 必须显式声明所用策略；任何单一选择都不能被报告为公共 Collapse Go 的最终行为。

### 3.2 差分规范投影

C++ 与 Python 对同一稳定前缀和同一候选原子行动至少比较：

1. 接受或拒绝及稳定错误类别；
2. 黑白占位与 stable source identities 的规范投影；
3. 当前 actor、phase、pending Double owner/linkage；
4. 原子行动数、阈值、PASS 连续数和触发状态；
5. 双方初始、剩余和已用配额；
6. 完整特殊事件账本、逻辑顺序、armed/tombstone/captured/settled disposition；
7. occupancy-only PSK 历史或严格语义等价的序列，包括每个玩家事件和每个 settlement pop 的稳定占位；
8. settlement 触发原因、全局 newest-to-oldest 顺序、每步 no-op/能力移除/同步提子/闭包和稳定轨迹；
9. 从精确状态派生的 legal mask；
10. 接受事件组、下一精确状态、下一修订和日志位置是否形成同一个语义提交；
11. 死子流程、恢复行棋、计分、认输、超时和终局中已经冻结的语义；
12. 调试模式下按坐标规范化的群、气、Eightway 连接和 Immortal 保护状态。

内存地址、容器迭代顺序、实现私有群 ID、缓存命中、墙钟、线程调度和搜索统计不属于规则语义比较项。

### 5.4 Double-Move

| ID | 场景与精确断言 |
|---|---|
| CG-DBL-001 | `DOUBLE_START` 是带审计标记的特殊点行动，接受时立即消费 Double 配额并创建 consumed/tombstone 事件；同一 actor 随后恰好再行动一次。 |
| CG-DBL-002 | continuation 只允许 NORMAL 或 PASS；IMMORTAL、DOUBLE_START、EIGHTWAY 和再次进入 pending Double 均被原子拒绝。 |
| CG-DBL-003 | `DOUBLE_START` 和 NORMAL continuation 分别执行各自完整的落子、提子、自杀与 PSK 合法性事务，分别形成稳定事件、日志项和 PSK 追加。 |
| CG-DBL-004 | PASS continuation 只验证 phase、actor 和 continuation 义务；它不放置棋子、不提子、不做自杀检查，也不做 PSK 重复拒绝检查。它仍增加 `A` 与 PASS 连计、形成独立接受事件、清除 pending Double、追加重复稳定占位并把行动权交给对手；若触发 settlement，该对手保留为 `handoffActor`。 |
| CG-DBL-005 | `A=T-2` 时 start 和 continuation 分别成为第 `T-1`、`T` 个原子行动；continuation 完整提交后才触发 settlement。 |
| CG-DBL-006 | Double 账本事件保留到 settlement；其 pop 为可见 no-op，仍产生稳定 PSK 追加，盘上 source stone 随后只按普通石处理。 |

|---|---|

## 6. 日志、动作、搜索、模型与端到端夹具

### 6.1 日志与协议语义

| ID | 场景与精确断言 |
|---|---|
| IO-LOG-001 | 从初始化和完整 JSON 权威事件日志重放，得到与在线 C++ 执行相同的精确状态、派生 legal mask 和结果。 |
| IO-LOG-002 | 非法、旧修订或不支持命令不追加事件，不改变下一状态或日志位置；幂等重发已接受命令只返回原结果。 |
| IO-LOG-003 | 对每个接受命令，接受结果、事件或事件组、下一精确状态、下一修订和已提交日志位置必须一起出现；崩溃注入不得恢复出撕裂组合。 |
| IO-LOG-004 | 截断日志、未知权威事件、未知主版本、错误规则身份和损坏 settlement transaction 必须明确拒绝，不静默降级。 |
| IO-LOG-005 | 快照与日志冲突时检测失败并以日志重放为恢复依据；缺少 PSK、账本、pending Double 或日志位置的快照不得独立续局。 |
| IO-LOG-006 | legal mask 作为派生读模型绑定权威修订；旧 mask、跨修订缓存和把 mask 写入 PSK 键的实现均被测试拒绝。 |

物理数据库事务、WAL、文件追加、ACK 时点和恢复机制尚未冻结；测试必须验证冻结的语义原子性，而不是把某一种持久化产品写成规则要求。

## 7. 撤销、重放、D4 与运行时检查

### 7.1 撤销、重做与检查点

- 对每个黄金夹具，在每个原子玩家行动前后执行撤销与重做，并比较完整规范投影。
- 必须覆盖 Double start 后的同方中间态、NORMAL/PASS continuation、`A=T-2`、第 `T` 个行动、settlement 前后、每个 settlement pop 的审计重放、post-settlement 行棋、死子分歧恢复和终局。
- 撤销 settlement 必须恢复能力状态、配额消耗事实、完整账本、PASS 状态、PSK 和日志位置；重做产生相同逻辑顺序和稳定状态。
- 从任意合法检查点追加同一后缀的结果必须等于从初始状态完整重放；检查点不得丢失 PSK、账本或 pending Double。

### 7.2 D4 一致性

每个可变换黄金局面必须覆盖八种 D4：

- 占位、特殊锚点、动作、捕获集合、群、气和派生 legal mask 按同一坐标映射等变；
- 规则身份、行动数、配额、账本顺序、PASS 和胜负不因几何变换改变；
- policy、逐动作 Q、legal mask、T0/T1 policy targets 与 visit counts 分别置换四个 361 点动作块；ownership 及任何空间型 survival/辅助 target 按每通道单一 19×19 点置换变换；global、标量及非空间 target 不变。不得在 survival 精确张量形状仍为 **UNFROZEN** 时预先固定其 action 布局；
- settlement 步数、no-op 位置和事件逻辑顺序不变，仅坐标集合变换；
- symmetry 及其 inverse 后，所有离散工件逐 bit 恢复。

### 7.3 ASan、UBSan 与调试不变量

- 规则核心、日志重放、撤销/重做、全部核心黄金夹具及早期差分运行的指定分层必须分别在 ASan 与 UBSan 构建中通过且零报告。
- 禁止宽泛 suppression 隐藏项目代码问题；第三方 suppression 必须精确、带来源并证明不覆盖 MutaGo/KataGo 自有路径。
- 调试构建在每个稳定边界检查：群/气缓存可由全盘重建复现；事件序位唯一；配额只递减；PSK 追加未丢失；不稳定 settlement 中间态未进入 PSK；pending Double 只开放 NORMAL/PASS；提交的状态修订与日志位置一致。

## 8. GATE-RULE-1M：早期一百万原子行动规则差分硬闸门

### 8.1 计数单位

一个计数单位是：从完全相同、可重放的稳定状态向 C++ 和 Python 提交同一个候选原子行动，并完成第 3.2 节的全部规则投影比较。

- 点行动或 PASS 各计一个；Double start 与 continuation 分别计数。
- settlement 内部 event pop 不计作随机玩家候选，但其完整稳定轨迹和每次 PSK 追加在触发行动的比较中逐项相等。
- 若双方都拒绝，仍计作一个非法候选，且双方状态、修订和日志位置必须不变。
- 若双方都接受，只有语义提交边界和全部投影比较通过后，才从新稳定状态继续。

### 8.2 闸门前置条件

- C++ 规则 reducer 与 Python oracle 已分别实现冻结的规则语义；
- 核心 GOLD/PROP/UNDO/REPLAY/SAN 夹具通过；
- Action Schema V1 codec 已通过全部 1445 ID 测试；
- 初始 PSK 播种策略已经为该合格运行明确冻结并写入 manifest；若公共决定尚未完成，只能生成非发布的候选证据，不能冒充最终 GATE-RULE-1M 证书；
- 运行绑定精确规则描述符字节。公共身份仍未分配时，报告必须明确标为内部候选描述符，不得发布占位哈希。

### 8.3 合格运行范围

- 至少 `1,000,000` 个合法与非法候选原子行动，零可复现 C++/Python 语义差异。
- 覆盖 9×9、13×13、19×19；官方双方 `1/1/1`；以及包含 `0`、大于 `1` 和混合值的非官方完整配额向量。
- 覆盖 NORMAL、IMMORTAL、DOUBLE_START、EIGHTWAY、PASS、NORMAL continuation、PASS continuation、配额耗尽、错误 phase 和终局后非法行动。
- 覆盖 `A=T-2`、`A=T-1`、第 `T` 个行动、阈值前双 PASS、settlement 前后、tombstone/no-op、PSK、普通自杀、Immortal 保护、Eightway 重建和死子流程的已冻结部分。
- 生成器以合法可达前缀为基础，并混入结构化非法候选；不得只使用某一个实现给出的“合法动作列表”来回避分歧。
- 具体采样权重、分层下限和种子清单为 **UNFROZEN**，但必须在运行开始前写入不可变 manifest，运行后不得为改善结果而修改。

### 8.4 失效与差异处理

合格计数必须发生在最后一次影响规则语义、C++ reducer、Python oracle、事件投影、PSK、settlement、动作 codec 或重放的修改之后，修复前后的计数不得相加。

发现差异时：

1. 立即保存测试描述符、初始 PSK 策略、构建信息、种子、完整前缀、候选行动和双方投影；
2. 自动最小化为最短可复现前缀并生成永久回归夹具；
3. 依据规范裁决并修复错误实现，不得简单让 Python 模仿 C++；
4. 从零重新运行至少一百万候选；
5. 无法解释的偶发差异继续阻塞，只有证明为外部工具或硬件故障并完成干净重跑后才能排除。

### 8.5 闸门后才能开始的工作

只有 GATE-RULE-1M 通过后，才允许开始：

- Collapse Go 搜索与转置集成；
- 生产 C++ gameplay 协议、Gateway/WebSocket 和客户端产品路径；
- 自博弈、replay、训练样本或其他数据 producer；
- 把 Model V19 接入可产生训练数据的 Collapse 环境。

该闸门不依赖 SEARCH、NN 或 E2E 完成；把这些后期条件并入早期闸门会造成依赖倒置，属于不合格路线。

## English Summary

C++ is the sole production rules authority; Python is a separately implemented slow oracle that produces reference semantics, not production-authoritative events. Both implementations must compare exact acceptance, errors, occupancy, actor and phase, quotas, event-ledger state, occupancy-only positional-superko history, every stable settlement closure, derived 1445-bit legality, scoring, termination, and the semantic commit boundary. `legalMask` is derived from exact state and is never a `GameState` field.

Testing is deliberately split into two gates. **GATE-RULE-1M** occurs immediately after the independent C++ and Python rule implementations and before any search integration, production gameplay protocol, Gateway/Web product path, self-play producer, or training-data producer. It requires the core golden/replay/undo/sanitizer suite and at least one million reproducible legal and illegal atomic-action comparisons with zero reproducible semantic differences. SEARCH, NN, and E2E are not prerequisites for this early gate.

The later **GATE-PROD** is the full production, training, release, and beta admission gate. It retains a still-valid million-action certificate and adds search, protocol, persistence recovery, Model V19, Inputs V9, Training Schema V1, Action Schema V1, D4, migration, SGF, Gateway/Web, end-to-end authority, provenance, identity, and release checks. Data generated before this later gate remains isolated development data and cannot be retroactively admitted to the formal training pool.

Official Collapse Go uses occupancy-only positional superko. Every accepted rule event’s stable post-state is appended; an action that triggers settlement appends its own stable closure first, then every newest-to-oldest settlement event pop appends its stable closure. Tombstone/no-op steps may append duplicates, settlement repetitions are allowed, and unstable rebuild/capture intermediates are excluded. Initial empty-board seeding remains unresolved and must be explicitly declared in every fixture and run manifest until frozen.

Action Schema V1 is kind-major: NORMAL `0..360`, IMMORTAL `361..721`, DOUBLE_START `722..1082`, EIGHTWAY `1083..1443`, and PASS `1444`, with `a=361*k+p`. A NORMAL Double continuation performs the full placement/capture/suicide-or-protection/PSK transaction. A PASS continuation performs none of those board-legality operations, but still increments the action and pass counters, emits its event, clears pending Double, appends unchanged stable occupancy, and hands play to the opponent; that opponent remains `handoffActor` if settlement follows.

Extended SGF tests follow the loss model declared by the eventual SGF profile; they do not presume universal JSON-to-SGF-to-JSON losslessness. Dead-stone dispute recovery details, initial PSK seeding, schema fields, persistence mechanics, and SGF properties remain explicitly unresolved. The public `rulesetId` and canonical-descriptor fields/canonicalization remain **UNFROZEN / unassigned**, while the final public descriptor SHA-256 remains **AUDIT-BLOCKED / unassigned**. The pinned baseline is KataGo stable v1.16.5 at `ba938676d7f42d70950b3a535af2466fb642008c`.
