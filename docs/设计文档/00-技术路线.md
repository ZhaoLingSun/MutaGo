## 1. 目标与非目标

### 1.1 目标

**[FROZEN]** MutaGo 在保留 KataGo 完整历史、许可证、贡献者、vendored notices 和源码布局的前提下，建立一个可扩展变体平台，并首先实现 Collapse Go。路线必须同时满足：

- C++ 是唯一生产规则、搜索和权威事件来源；
- Python 规则 oracle 独立实现、缓慢但可解释，可与 C++ 做逐行动差分；
- 搜索不再假设每条边都交换行动者，也不把能力结算暴露为决策节点；
- 线上协议、事件日志、网关和客户端不复制规则；
- 早期一百万行动规则差分硬闸门必须先于搜索、协议、网关、客户端和训练数据生产；
- 后续生产者/训练准入是独立门槛，只有特征、回放、自对弈、推理后端和端到端恢复均通过后，数据才可进入正式训练池；
- 普通围棋能力和训练回放得到保留，而不是被 Collapse Go 单一分布覆盖。

### 1.2 非目标

**[FROZEN]** 当前路线不承诺：

- 在首提交中提供任何可运行功能；
- 让上游 KataGo 模型直接兼容 Collapse Go；
- 让 9×9 或 13×13 成为正式竞赛规则；
- 支持让子、FP8、分布式社区训练或公开稳定发行；
- 维持上游分析协议、SGF 或哈希结构对新规则的二进制兼容；
- 由 Node、浏览器或神经网络近似替代精确合法性和 PSK。

## 2. 路线所依赖的冻结语义

### 2.1 规则基础

**[FROZEN]** 正式 v0.1 是空 19×19 平手棋，黑先，白贴目 7.5，中国式数子法，采用只看黑白占据且不包含下一手玩家的 occupancy-only 位置超级劫（`PositionalSuperkoKey` / PSK），无让子。`0.1.0-draft` 中已经列明的玩法语义仍是冻结合同；9×9、13×13 仅作实验。阈值为：

\[
T(N)=\left\lfloor\frac{150N^2+180}{361}\right\rfloor,
\quad T_9=34,\ T_{13}=70,\ T_{19}=150.
\]

实际落子与 `PASS` 各计一个全局原子行动。Double 起手和续手分别计数。特殊能力从行动 1 开放；Immortal/Eightway 可用在行动 `T`；Double 起手必须不晚于 `T-1`。行动 `T` 先完整执行、写入历史并成为最新事件，然后触发能力结算。

每方正式完整配额向量为 Immortal、Double-Move、Eightway 各 1，即 `1/1/1`。合法特殊落子提交即永久消耗配额；被提不返还，未使用配额在能力结算后失效。任何与官方 `1/1/1` 不同的完整配额向量必须进入不同规范化描述符并使用不同规则哈希；语义完全相同的配置不能仅因“experimental”运行标签而获得不同身份。

达到 `T` 或 `T` 前连续两次 `PASS` 触发一次能力结算；连续两次停着在此处不计分。结算结束后重置停着连计，只开放普通围棋行动，之后需要新的连续两次 `PASS` 才进入终局。认输和游戏语义超时只在暴露的稳定命令边界接受：若先于候选动作提交，则立即判负且不提交该动作、不执行其 settlement 或计分；动作一旦提交，其触发的 settlement 必须原子完成，内部没有终止命令边界。传输/请求超时、取消、断连与背压不得合成游戏 `TIMEOUT`。

### 2.2 搜索与模型基础

**[FROZEN]** 固定 19×19 模型画布；9×9、13×13、19×19 分别以 `(5,5)`、`(3,3)`、`(0,0)` 嵌入，D4 围绕 `(9,9)`。Action Schema V1 使用 kind-major 编码：`k=0,1,2,3` 依次为 `NORMAL`、`IMMORTAL`、`DOUBLE_START`、`EIGHTWAY`，画布点索引 `p∈[0,360]`，动作 ID 为 `a=361*k+p`。因此 `NORMAL=0..360`、`IMMORTAL=361..721`、`DOUBLE_START=722..1082`、`EIGHTWAY=1083..1443`、`PASS=1444`。网络固定输出 1445 个槽位，C++ 环境另外生成精确合法掩码；完整 ABI 见[04-输入特征ABI-V9.md](04-输入特征ABI-V9.md)。

Double 使用两个 MCTS 决策节点；起手后行动者不变，续手只允许 `NORMAL/PASS`。能力结算是 reducer 内部确定性闭包，不产生搜索节点。网络价值相对当前玩家，在叶节点只转换一次为白方为正的 `Q`；白方选择最大 `Q`，黑方选择最大 `-Q`，不得依据深度奇偶翻号。

## 3. 总体依赖原则

**[FROZEN]** 实施依赖为：

1. 先冻结语义和可序列化契约；
2. 再建立独立 Python oracle 与黄金向量；
3. 再实现 C++ 权威 reducer；
4. 通过早期 C++/Python 规则差分硬闸门；
5. 只有此后才能启动搜索、协议、网关、客户端和训练数据生产者的实现与数据生成；
6. 这些生产者仍须通过后续完整生产/训练准入门槛，数据才可进入正式训练池，系统才可宣称训练就绪；
7. 模型与数据池永远不能成为规则正确性的前置条件。

阶段是依赖关系，不是必须串行的日历。早期规则差分门槛只证明规则 reducer 的双实现一致性，不等同于搜索、协议、特征、回放、自对弈或发行已经就绪。它通过后，搜索泛化与产品协议可以并行；正式训练仍必须等待 Action Schema V1、Inputs V9、Training Schema V1、生产者一致性和推理后端的独立准入。

## 5. 规则内核工作流

### 5.1 `GameState + VariantReducer`

**[FROZEN]** `GameState` 是不可拆分的权威聚合体，至少覆盖占据、棋子/能力来源、行动者、阶段、Double 待续手、全局行动数、停着连计、双方配额、特殊事件账本、完整 PSK 上下文和终局状态。不得让 `Board`、历史、行动者和变体字段由不同层独立修改。

`VariantReducer` 负责：

- 生成精确合法行动及 1445 位掩码；
- 应用一个原子行动并保证强事务；
- 在触发点执行完整能力结算闭包；
- 产生权威事件、状态与轨迹；
- 为搜索、PSK、NN 和协议提供各自投影；
- 依据事件日志确定性重放。

### 5.2 落子事务

**[FROZEN]** 所有落子种类复用同一事务骨架：在候选状态放置棋子并应用该行动种类的锚点语义；重建混合连接、气与保护；同时删除所有对方零气且未受保护的组；重建；要求新落子所在己方组有气或由存活 Immortal 保护；对最终黑白占据检查 PSK；通过后原子提交。失败必须连同配额、标记、事件 ID 和行动计数一起回滚。

PSK 只比较黑白占据，排除行动者、标记、配额、行动号和阶段。每次点行动都检查最终占据；`PASS` 豁免 PSK 重复拒绝检查，但仍提交动作事件并把未改变的稳定占据追加到历史。完整占据历史跨能力结算和终局前普通对局持续存在。

### 5.3 能力结算闭包

**[FROZEN]** 结算处理双方所有已使用特殊事件，以稳定原子事件 ID 全局从新到旧排序。每次只停用一个事件的能力：若锚点仍在，棋子留下并转为普通棋子；若已被提，事件仍作为审计无操作；Double 机械上也是无操作。随后重建全盘，所有颜色的零气未保护组同时删除，再重建并防御性重复到不动点。每个事件完成后的这一稳定黑白占据都必须追加到 occupancy-only PSK 历史，然后才处理下一事件；能力移除、重建或提子过程中的不稳定中间棋盘不得写入 PSK。

闭包对搜索是一个原子转换，但必须产生完整有序轨迹供 UI、重放与审计使用。轨迹开关不能改变最终状态、键或事件内容。结算产生的重复占据允许存在并写入历史，且会约束未来玩家落子；PSK 不得阻断结算。

## 6. 搜索路线

### 6.1 行动与节点

**[FROZEN]** 搜索边携带完整语义行动，不再只携带点位。Double 起手形成真实子状态：能力已消耗、标记已落、行动者不变、阶段为强制续手。`NORMAL` continuation 独立执行完整落子、提子、自杀/保护及 PSK 合法性事务。`PASS` continuation 只验证 phase、actor 和 continuation 义务；它不落子、不提子、不检查自杀，也不执行 PSK 重复拒绝，但仍增加 `A` 与停着连计、产生动作事件、清除 pending Double，并追加未改变的稳定占据。任一合法 continuation 完整提交后，下一行动者确定为该行动者的对手；若触发 settlement，该对手保存为 `handoffActor`，结算完成后仍由其行动。

搜索键必须等价于“未来行为完全相同”，因此至少覆盖规则身份、占据与存活能力、行动者、阶段、Double 上下文、配额、计数、停着、结算所需账本、终局和精确 PSK 上下文。不能以当前盘面哈希代替。

### 6.2 值与网络边界

**[FROZEN]** 网络输出相对当前玩家。叶节点评估后只进行一次白方为正转换：当前玩家为白时保持，当前玩家为黑时取反。树内不做深度奇偶翻号。白节点按 `Q` 选择，黑节点按 `-Q` 选择。

精确 PSK 永远属于环境状态。网络可以接收经版本化定义的历史和计数特征，但不得重构或近似合法性；合法掩码由 C++ reducer 逐状态产生，并在任何策略归一化与采样前应用。

## 7. 模型与迁移路线

### 7.1 固定模型家族

**[FROZEN]** 使用一个多规则条件模型，覆盖普通围棋 `0-0-0` 与 Collapse 变体。主干为残差/嵌套瓶颈 CNN，并周期性插入全盘 Transformer；包含 D4-orbit 相对偏置、KataGo 式 global-pooling bias、经验 D4 增广与一致性约束，可选 8 路对称推理集成。

| 配置 | 通道 | CNN macro | Transformer | attention width | heads |
|---|---:|---:|---:|---:|---:|
| Debug | 96 | 4 | 2 | 64 | 4 |
| Base | 256 | 10 | 4 | 128 | 4 |
| Large | 384 | 12 | 5 | 192 | 6 |

目标版本为 Model V19、Inputs V9、Training Schema V1、Action Schema V1。Inputs V9 恰好为 38 个空间特征和 67 个全局特征；上游 22 个空间索引、19 个全局索引和 `G18` 的精确保留方式已经由[04-输入特征ABI-V9.md](04-输入特征ABI-V9.md)冻结。当前 M0 已实现 Action V1 的关闭式 Schema、kind-major codec、黄金向量和 C++/Python 合同测试；Model V19、Inputs V9、Training Schema V1 及 Action V1 在搜索、协议和训练生产链路中的集成仍未实现。后续实现必须使用该文档的精确索引、归一化、视角、历史、合法掩码和动作布局。上游当前版本边界可参见 [`modelversion.h`](../../cpp/neuralnet/modelversion.h) 与 [`nninputs.h`](../../cpp/neuralnet/nninputs.h)。

保留 KataGo 的 policy、value、score belief 和 ownership 能力，新增：

1. 能力结算后占据预测；
2. 棋子存活预测；
3. 特殊事件存活预测。

三个辅助头的精确张量、目标视角和损失权重为 **[UNFROZEN]**。

### 7.2 Donor 与迁移

**[FROZEN]** donor 为：

- Debug：`kata1-b6c96-s175395328-d26788732`，并保留 scratch control；
- Base：`kata1-b40c256-s10800760064-d2633359377`；
- Large：`kata1-b18c384nbt-s9996604416-d4316597426`。

迁移清单必须逐张量映射 donor 与 Model V19，并遵守[04-输入特征ABI-V9.md](04-输入特征ABI-V9.md)的确定性迁移合同；禁止用盲目的 `strict=False` 接受缺失或多余参数，也禁止借“扩通道”工具引入随机扰动。

冻结初始化与状态迁移策略为：

- 只有 donor 工件中实际存在、完成来源审计且语义兼容的 raw-model 参数才逐 bit 复制；新参数精确置零；
- 旧普通点策略复制到 `NORMAL` 块，旧 `PASS` 复制到 1444，三个特殊动作 policy 块精确置零；三个已选 donor 均不含逐动作 Q，Model V19 的全部 Q 参数及状态新建并精确置零，不声称从 donor remap；
- 只有 donor 实际携带且 manifest 证明兼容的 EMA/SWA 参数和 `n_averaged` 才复制；缺失或新增的平均参数/状态显式零初始化，且不得伪造为 exact-copy；
- 只有 donor 实际携带且 manifest 证明兼容的 optimizer buffers、step 和 parameter-group 超参数才复制；公开 Debug/Base/Large 工件均不提供可直接 exact-copy 的 PyTorch optimizer，目标 optimizer 状态显式零初始化；
- 描述符更新为 Model V19、Inputs V9、Action Schema V1 和 Training Schema V1；
- 保留 donor 中实际存在且语义兼容的其他 train state；不得静默删除实际存在的状态，也不得把缺失的 optimizer、EMA/SWA、metrics 或 Q 状态写成已迁移。

精确 donor 参数名、切片范围和每个后端导出映射仍为 **[AUDIT-BLOCKED]**；这不改变上述已经冻结的迁移不变量。

### 7.3 课程、数据与验证

**[FROZEN]** 课程从小棋盘和单能力开始，随后能力配对，再到正式 `1-1-1`。普通围棋回放必须持续保留。训练池按稀有事件分层，至少覆盖零气保护、Eightway 对角连接、Double 续手、阈值行动、结算连锁、PSK 与终局。

根节点噪声按行动类型感知，避免 1444 个空间槽位中的类别不平衡。联赛至少包含当前模型、历史模型、针对性 counter 和普通围棋 anchor。先建立同步验证闭环，再启动异步 worker。

BF16 是基线；FP8 延后。目标硬件为 1–4 张 RTX 5090，但硬件数量不是正确性豁免。任何社区分布式训练或公共模型分发必须等待稳定 beta。

## English Summary

This roadmap is dependency-driven, not a date commitment. The historical Phase 0 was a documentation-only repository-boundary bootstrap. The current M0 milestone has since added authorized source schemas, golden vectors, contract tooling, C++/Python contract code, and tests; it still does not claim a complete Collapse Go reducer, product stack, model/training implementation, tag, or release.

The implementation order is: preserve the frozen `0.1.0-draft` gameplay semantics and M0 public identity `mutago.collapse-go` / `0.1.0-draft` / `a21c67d7962b71a3a53b895de824dc6312502362de5341103c0265c2c81d0899`; build an independently implemented Python oracle; implement the authoritative C++ `GameState + VariantReducer`; pass the early hard differential rule gate; only then build search, protocols, the thin Node gateway, the rendering-only React client, and training-data producers.

The early rule gate requires at least one million randomized legal and illegal atomic actions with zero reproducible C++/Python differences plus all rule fixtures, ASan/UBSan, undo/redo, D4, occupancy-only PSK, threshold, and settlement-trace checks. It is not a production/training-readiness claim. A later independent gate must validate Inputs V9, Action/Training Schema implementations, replay and self-play producers, model export/inference, deterministic recovery, and producer/consumer consistency before any data enters the formal training pool.

Search must use semantic actions, preserve the actor across `DOUBLE_START`, expose only `NORMAL/PASS` during continuation, and treat settlement as one deterministic edge. A Normal continuation performs the full placement/capture/survival/PSK transaction. A Pass continuation performs none of those board-legality operations, but still increments action/pass counters, emits its event, clears pending Double, appends unchanged occupancy, and hands play to the opponent; that opponent remains `handoffActor` if settlement follows. Network values are current-player-relative and are converted once at the leaf to white-positive `Q`; backups never flip by depth parity.

The target model family combines residual/nested-bottleneck CNNs with periodic global Transformers, D4-orbit bias, KataGo-style global-pooling bias, D4 augmentation/consistency, and an optional eight-symmetry ensemble. Debug/Base/Large are fixed at `C96/4/2/64/4`, `C256/10/4/128/4`, and `C384/12/5/192/6`. The frozen contracts are Model V19, Inputs V9 with exactly 38 spatial and 67 global features, Training Schema V1, and Action Schema V1. The action codec is kind-major: NORMAL 0–360, IMMORTAL 361–721, DOUBLE_START 722–1082, EIGHTWAY 1083–1443, and PASS 1444.

Donor migration must follow the frozen deterministic ABI migration contract. Raw-model, EMA/SWA, optimizer, counters, hyperparameters, and other train state are copied only when the audited donor artifact actually contains a semantically compatible item; missing or new state is explicitly zero-initialized and never fabricated as an exact copy. The selected donors contain no per-action Q, so all Model V19 Q parameters and state start at exact zero rather than being remapped. Special policy branches also start at exact zero. Exact donor tensor maps and backend implementation compatibility remain audit-blocked, but the indexed Inputs V9 and Action Schema ABI are already frozen in [04-输入特征ABI-V9.md](04-输入特征ABI-V9.md).

Training retains ordinary Go replay, uses a small-board/single-ability-to-`1-1-1` curriculum, rare-event strata, action-type-aware root noise, and current/history/counter/ordinary-anchor leagues. Synchronous validation precedes asynchronous workers. BF16 is the baseline, FP8 is deferred, the target hardware is 1–4 RTX 5090 GPUs, and community distribution waits for a stable beta.
