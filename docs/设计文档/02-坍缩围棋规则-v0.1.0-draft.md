## 3. 术语、事件与概念状态

本节中的大写动作名是规则语义及 Action Schema V1 的固定动作名。Action V1 的 canonical envelope 字段已冻结为 `schemaVersion`、`actionId`、`kind`；后续生产命令/事件封装和人类文本坐标仍为 **UNFROZEN**，但不得据此改名、合并或重排这些动作。

### 3.1 原子动作（atomic action）— FROZEN

一个原子动作是一次已经合法并提交的：

1. 落子，包括 `NORMAL`、`IMMORTAL`、`DOUBLE_START` 的起始落子、`EIGHTWAY`，以及 `DOUBLE_START` 的 `NORMAL` 续着；或
2. `PASS`。

非法请求、格式错误请求、试探性局面、结算移除、认输和游戏语义超时都不是原子动作，不增加全局动作计数。未来语义版本若引入死子协商，其管理命令也不得冒充原子棋盘动作。

### 3.2 回合（turn）— FROZEN

回合是某位行动者取得行棋权，到行棋权应交给对手为止的完整单位：

- 普通回合恰含一个原子动作；
- 使用 `DOUBLE_START` 的回合恰含两个原子动作：起始 `DOUBLE_START` 落子和同一玩家的强制续着；
- `DOUBLE_START` 起始落子后存在一个稳定状态，但行棋权尚未交给对手；
- 强制续着提交后，行棋权才交给对手。

### 3.3 阶段（phase）— FROZEN

规则状态具有以下互斥阶段：

1. `COLLAPSE_PLAY`：坍缩前行棋，可使用尚有配额且满足动作编号限制的特殊能力；
2. `SETTLEMENT`：一次性的、无玩家决策点的坍缩结算；
3. `ORDINARY_PLAY`：结算后的普通围棋，只允许普通落子和停着；
4. `TERMINAL`：已经以计分、认输或超时结束。

MVP 不启用额外的人类死子协商阶段：`ORDINARY_PLAY` 持续到两个连续 `PASS`，随后直接按当前稳定盘面计分。未来版本若增加协商移除或争议恢复，必须另行版本化，不得改变本 MVP 路径。

### 3.4 事件（event）— FROZEN

规则事件是权威事件流中的语义记录：

- 每个原子动作提交一个动作事件；
- 结算中每处理一个已用特殊事件，提交一个结算步骤事件；
- 计分、认输或超时可提交终局事件。

每个已提交特殊落子事件都具有唯一、确定、可全序比较的起源顺序键。实现可以使用单调 `stableEventId`，或与全局原子动作序号一致的逻辑时间；不得以可能碰撞或受机器时钟影响的墙上时间决定结算顺序。具体编码仍为 **UNFROZEN**。

传输层信封、重试记录和日志注释不是本规则所称的事件。

### 3.5 稳定状态（stable state）— FROZEN

稳定状态是一次动作事务或一次结算闭包已经全部完成后的状态。试探性落子、捕获集合尚未同时移除的盘面、结算闭包的中间迭代都不是稳定状态，不能成为玩家决策节点。

每个产生稳定后状态的规则事件之后，都必须把该稳定黑白占用追加到有序 PSK 历史；重复占用仍保留为独立历史记录。试探性落子、重建、分批提子及结算闭包尚未完成时的不稳定中间盘面不得进入 PSK 历史。

初始化时，初始空盘的黑白占据必须预先写入有序 PSK 历史，索引固定为 `0`。因此，在任何规则事件提交前，历史已经包含且仅包含这一条初始空占据。

### 3.6 已用特殊事件与活锚点 — FROZEN

- **已用特殊事件**：一次已经合法提交的 `IMMORTAL`、`DOUBLE_START` 或 `EIGHTWAY` 起始落子事件。棋子后来被提走也不删除该事件。
- **活不灭锚点**：其不灭事件尚未在结算中失效，且对应棋子仍在盘上的不灭棋子。
- **活八方锚点**：其八方事件尚未在结算中失效，且对应棋子仍在盘上的八方棋子。
- `DOUBLE_START` 的机械能力在起始落子提交时即被消耗；其事件仍是已用特殊事件，并在结算中占据一个可审计的无操作步骤。

### 3.7 结算闭包（settlement closure）— FROZEN

在某一个特殊事件失效后，反复执行“全盘重建；找出所有零气且不受保护的棋块；同时移除这些棋块”，直至不存在这样的棋块。闭包最终盘面才是该结算步骤的稳定状态。

### 3.8 概念状态 — FROZEN

规则归约器至少必须能够确定下列语义信息；并不要求采用同名内存结构：

- 棋盘尺寸及黑、白、空占用；
- 盘上棋子对其起源特殊事件的引用；
- 当前阶段和当前行动者；
- 是否存在 `DOUBLE_START` 强制续着及其行动者；
- 全局已提交原子动作数 `A`；
- 当前连续停着数；
- 每方各特殊能力的剩余配额；
- 所有已用特殊事件、其顺序和是否仍有机械效果；
- 完整、有序、允许重复的 PSK 占用历史；
- 权威事件日志。

当前行动者、续着义务和终局状态均由权威归约器给出，不由客户端推断。

### 3.9 动作名与 Action Schema V1 — FROZEN ABI

Action Schema V1 使用 19×19 画布和 kind-major 编码。对画布坐标 `0≤X,Y<19`，定义：

\[
p=19Y+X,
\qquad
a=361k+p.
\]

等价的整数表达式为 `a=361*k+p`。固定 kind code 与动作范围为：

| `k` / 范围 | 动作 |
|---:|---|
| `k=0`，`a=0..360` | `NORMAL` |
| `k=1`，`a=361..721` | `IMMORTAL` |
| `k=2`，`a=722..1082` | `DOUBLE_START` |
| `k=3`，`a=1083..1443` | `EIGHTWAY` |
| `a=1444` | `PASS` |

因此动作顺序严格为 `NORMAL`、`IMMORTAL`、`DOUBLE_START`、`EIGHTWAY`、`PASS`，总数固定为 1445。规则和搜索中的动作身份必须区分 kind 与点；裸点坐标不能代表一个完整动作。9×9、13×13、19×19 棋盘分别按 `(5,5)`、`(3,3)`、`(0,0)` 偏移居中到 19×19 画布，D4 围绕画布中心 `(9,9)`；所选棋盘 footprint 外的所有点动作均非法，`PASS=1444` 不随棋盘尺寸变化。Action V1 规范线格式是关闭式对象，**恰好**包含 `schemaVersion`、`actionId`、`kind`；坐标由 `actionId` 唯一导出。缺失字段、任意未知字段、冗余坐标、未知 schema 版本和不一致的 `kind`/ID 组合必须 fail closed。完整 ABI 见 [`04-输入特征ABI-V9.md`](04-输入特征ABI-V9.md)。

## 4. 棋盘拓扑、棋块、气与保护

### 4.1 邻域 — FROZEN

设棋盘交叉点为 `p=(x,y)`，越过棋盘边界的点不存在。

- `N4(p)`：与 `p` 上、下、左、右正交相邻的盘内点；
- `N8(p)`：与 `p` 正交或对角相邻的所有盘内点，即切比雪夫距离为 1 的点。

对盘上棋子 `s`，定义其接口：

\[
I(s)=
\begin{cases}
N8(s), & s\text{ 是活八方锚点};\\
N4(s), & \text{其他情况}.
\end{cases}
\]

### 4.2 同色连接 — FROZEN

两个同色棋子 `u`、`v` 之间存在无向连接，当且仅当：

\[
v\in I(u)\quad\text{或}\quad u\in I(v).
\]

因此：

- 正交相邻的同色棋子总是连接；
- 对角相邻的同色棋子，仅当至少一个端点是活八方锚点时连接；
- 连接关系是无向的，即使只有八方端点暴露该对角接口；
- 不同颜色永不连接；
- 八方锚点两侧的“肩点”是否被占据不切断其直接对角连接。

一个棋块是上述同色无向图的极大连通分量。每次规则要求“重建”时，必须从当前盘面和当前仍然存活的能力重新计算，不能沿用历史棋块身份。

### 4.3 棋块的气 — FROZEN

棋块 `G` 的气是其成员接口所触及的所有空点的去重并集：

\[
L(G)=\{q\mid q\text{ 为空，且存在 }s\in G,\ q\in I(s)\}.
\]

同一个空点即使被多个成员接口触及，也只算一口气。任何已被黑子或白子占据的点都不是气。

### 4.4 不灭保护 — FROZEN

棋块 `G` 受保护，当且仅当 `G` 当前包含至少一个活不灭锚点。保护是动态属性：

- 它沿当前混合连接图覆盖整个同色棋块；
- 它可以经过活八方锚点建立的对角连接传播；
- 棋块分裂后，只有仍含活不灭锚点的碎片受保护；
- 一个碎片含有多个不灭锚点时，只要至少一个仍活着，保护仍在；
- 历史上曾与不灭锚点连接，不产生永久保护。

### 4.5 稳定盘面不变量 — FROZEN

在任一可继续行棋的稳定状态中，每个零气棋块都必须受活不灭锚点保护。零气受保护棋块可以持续存在；零气且不受保护的棋块不得留在稳定状态中。

## 5. 全局动作计数、阈值与配额

### 5.1 阈值公式 — FROZEN

对 `N×N` 棋盘：

\[
T(N)=\left\lfloor\frac{150N^2+180}{361}\right\rfloor.
\]

实现应使用精确整数运算：

```text
T = (150 * N * N + 180) div 361
```

已验证：

- `T(9)=34`；
- `T(13)=70`；
- `T(19)=150`。

### 5.2 动作编号 — FROZEN

初始化时 `A=0`，下一个合法提交的原子动作编号为 `i=A+1`。每次实际提交的落子或停着都使 `A` 增加 1：

- 每个普通落子计 1；
- 每个特殊起始落子计 1；
- `DOUBLE_START` 的续着另计 1；
- 每个 `PASS` 计 1；
- 结算步骤不计数。

动作编号从 1 开始，特殊能力从动作 1 即可使用，没有等待期。

全局计数在结算后继续单调增加；阈值只在 `COLLAPSE_PLAY` 中触发一次。若因阈值前双停着而提前结算，之后即使 `A` 达到原阈值也不得再次结算。

### 5.3 特殊动作的编号限制 — FROZEN

在 `COLLAPSE_PLAY` 且没有待完成的 `DOUBLE_START` 续着时：

- `IMMORTAL` 可作为动作 `1..T`；
- `EIGHTWAY` 可作为动作 `1..T`；
- `DOUBLE_START` 仅在执行前满足 `A+2≤T` 时合法，等价于其起始落子只能作为动作 `1..T-1`；
- 当执行前 `A=T-2` 时，`DOUBLE_START` 是动作 `T-1`，其强制续着就是动作 `T`；
- 当执行前 `A=T-1` 时，不得开始 `DOUBLE_START`。

该限制保证结算永远不会截断强制续着。

### 5.4 官方配额 — FROZEN

每位玩家各有：

- 1 次 `IMMORTAL`；
- 1 次 `DOUBLE_START`；
- 1 次 `EIGHTWAY`。

一次特殊落子只有在整个动作合法提交时才永久消耗相应配额。非法尝试不消耗配额。特殊棋子后来被提走不返还配额。结算开始时，所有未用配额直接失效，不得兑换分数、额外动作或其他补偿。

引擎可以支持任意非负整数的实验配额向量，但完整配额向量必须进入规范语义描述符；任何不同于官方每方 `1/1/1` 的配置都必须使用不同规则哈希。

## 6. 三种特殊能力

### 6.1 不灭（IMMORTAL）— FROZEN

1. 起始动作在一个空点放置本方不灭棋子，并使用第 8 节的统一落子事务。
2. 在试探性重建中，该新棋子立即作为活不灭锚点参与保护判定。
3. 含活不灭锚点的整个当前同色棋块免于因零气而被移除。
4. 因此，不灭棋子可以落在零气点；只要落子事务结束时新棋块仍含该活锚点，零气本身不使动作非法。
5. 普通棋子可以落下并连接到一个零气受保护棋块；合并后的棋块仍因包含活不灭锚点而受保护，前提是占用和 PSK 检查合法。
6. 保护始终服从当前混合连接。连接变化导致分裂时，仅含活不灭锚点的碎片继续受保护。
7. “两眼活”“真眼”或其他通常围棋的生命判断不能覆盖本规则。不灭棋子可以侵入普通真眼，在零气状态存活，并通过后续合法动作破坏普通两眼棋块。
8. 当该不灭事件在结算中失效时，棋子若仍在盘上就成为普通棋子；随后同一步结算闭包可能将其或相关零气碎片移除。

### 6.2 连着下（Double-Move；起始动作 `DOUBLE_START`）— FROZEN

1. `DOUBLE_START` 的第一个原子动作必须是落子，不能以停着开始。
2. 该动作放置一枚带有连着下标记的本方棋子。该棋子自身没有额外连接、气、保护、捕获或计分能力；它按普通棋子使用 `N4` 接口，但仍可通过其他活锚点的规则加入混合棋块或受保护棋块。
3. 起始落子独立执行捕获、自身存活检查和 PSK 检查，提交后形成稳定状态、动作事件和历史记录，并立即永久消耗 `DOUBLE_START` 配额。
4. 提交后同一玩家必须完成恰好一个合法续着。允许的续着仅为：
   - `NORMAL` 落子；或
   - `PASS`。
5. 续着不得使用 `IMMORTAL`、新的 `DOUBLE_START` 或 `EIGHTWAY`。
6. “恰好一个续着”指一个合法提交的续着，而不是一次请求机会。非法续着请求不计数、不改变状态，也不解除续着义务；`PASS` 始终提供可完成续着的选择。
7. `NORMAL` 续着独立执行完整落子事务；`PASS` 按停着规则提交。两者都各自增加全局动作计数并产生事件和稳定历史记录。
8. 续着提交后，行棋权交给对手。若续着是动作 `T`，先完整提交该续着，再执行结算；结算后仍由该对手行动。
9. 连着下的机械能力在起始动作提交时已消耗。标记在结算前必须可由权威状态或日志恢复并用于显示、审计；在结算中该事件按其全局顺序产生一个无机械变化的结算步骤。结算后若棋子仍在盘上，它只是普通棋子，永久审计身份留在事件账本中。

结算动画中标记究竟在该事件步骤、结算入口还是结算完成帧消隐属于 **UNFROZEN**；任何选择都不得影响棋盘、合法性、PSK、计分或事件账本。

### 6.3 八方（EIGHTWAY）— FROZEN

1. 起始动作在一个空点放置本方八方棋子，并使用统一落子事务。
2. 只有该枚活八方锚点自身使用 `N8` 接口。与它同块的普通棋子仍各自使用 `N4` 接口。
3. 对角连接由“任一端点是活八方锚点”建立，并按无向边处理。
4. 棋块的气是所有成员各自接口所触及空点的去重并集；八方能力不会把已占用点变成气。
5. 两个普通棋子不会仅因对角接触而连接；不同颜色永不因八方能力连接。
6. 八方锚点对角线两侧肩点上的棋子不切断直接对角连接。
7. 八方能力本身不提供不灭保护。零气八方棋块只有在同块还含活不灭锚点时才能存活。
8. 八方棋子可像普通棋子一样被合法提走；被提走不返还配额，其事件仍参加结算并成为无操作步骤。
9. 八方事件在结算中失效后，盘上该棋子立即改用 `N4` 接口。全盘重建可能使原棋块分裂，并触发结算闭包移除。

## 7. 回合状态机与坍缩触发

### 7.1 各阶段允许的玩家动作 — FROZEN

| 状态 | 允许动作 |
|---|---|
| `COLLAPSE_PLAY`，无续着义务 | `NORMAL`、`PASS`，以及满足编号和配额条件的三种特殊起始落子 |
| `COLLAPSE_PLAY`，有 `DOUBLE_START` 续着义务 | 仅同一玩家的 `NORMAL` 或 `PASS` |
| `SETTLEMENT` | 不接受任何玩家动作 |
| `ORDINARY_PLAY` | 仅 `NORMAL` 或 `PASS` |
| `TERMINAL` | 不接受行棋动作 |

认输和游戏语义超时不是棋盘动作；只有当 C++ 在暴露的稳定决策边界、且在候选原子动作提交前接受它们时，才立即终局。动作一旦提交，其触发的 settlement 必须先完整结束。

### 7.2 连续停着 — FROZEN

- 任意已提交落子，包括 `DOUBLE_START` 起始落子和续着落子，都把连续停着数重置为 0；
- 每个已提交 `PASS` 把连续停着数增加 1；
- `DOUBLE_START` 起始落子会清零此前停着，因此其续着停着最多成为新的第一手停着；随后对手停着可以成为第二手；
- 进入结算时，无论触发原因为何，连续停着数都重置为 0。

### 7.3 触发判定 — FROZEN

每个 `COLLAPSE_PLAY` 原子动作完整提交后，按下列规范顺序判定：

```text
if A == T:
    trigger settlement with reason THRESHOLD
else if A < T and consecutivePasses == 2:
    trigger settlement with reason PRE_THRESHOLD_TWO_PASSES
else:
    continue COLLAPSE_PLAY
```

因此：

- 动作 `T` 总是先完整执行合法性、捕获、PSK、提交、事件记录和历史追加；
- 动作 `T` 在任何结算步骤之前是最新动作事件；
- 若动作 `T` 本身是 `IMMORTAL` 或 `EIGHTWAY`，它是最新已用特殊事件，并在结算队列中最先失效；
- 若第二个连续停着恰好是动作 `T`，规范触发原因是 `THRESHOLD`，而不是“阈值前双停着”；
- 两个连续停着只有在第二手编号严格小于 `T` 时才提前触发结算；
- 阈值前双停着触发的是结算，不是计分，也不是整盘终局。

### 7.4 结算后的行动者 — FROZEN

触发动作所在回合完成时，先按正常规则确定本应接手的对手，并保存为 `handoffActor`。结算不消耗回合、不交换额外行动权。结算完成后，`handoffActor` 成为 `ORDINARY_PLAY` 的当前行动者。

动作 `T` 不可能是尚未完成的 `DOUBLE_START` 起始动作：起始编号最多为 `T-1`，动作 `T` 只可能是其续着或一个普通回合的动作。因此结算总在完整回合边界开始。

## 8. 统一落子与停着事务

### 8.1 所有落子的有序合法性算法 — FROZEN

`NORMAL`、`IMMORTAL`、`DOUBLE_START` 起始落子、`EIGHTWAY` 和 `DOUBLE_START` 的 `NORMAL` 续着必须使用同一个有序事务。

1. **前置验证**：验证阶段、当前行动者、续着限制、动作编号限制、配额和目标点为空。
2. **建立试探状态**：在副本中放置本方棋子。若为不灭或八方，该锚点立即以“活”状态参加本次试探重建；若为连着下，其棋子仅带非机械标记。
3. **第一次全盘重建**：按第 4 节重建两色混合棋块、气和不灭保护。
4. **确定对手待移除集合**：找出所有“零气且不受保护”的对手棋块，以同一次重建结果为依据取其并集。
5. **同时移除对手棋块**：一次性移除整个待移除集合；不得按任意顺序逐块移除并在中间改变判定。
6. **第二次全盘重建**：在捕获后的盘面重新计算混合棋块、气和保护。
7. **检查本方新棋块**：包含新落棋子的当前本方棋块必须满足 `至少一口气` 或 `包含活不灭锚点而受保护`。否则动作因自杀非法。
8. **检查位置超级劫**：计算仅含黑白占用的候选 PSK 键；若该占用已在完整历史中出现，动作非法。
9. **原子提交**：仅在以上检查全部通过后，一次性提交盘面、捕获、特殊配额消耗、动作计数、事件、标记或锚点状态、连续停着更新和 PSK 历史追加。
10. **更新回合状态**：`DOUBLE_START` 起始落子建立同一玩家的续着义务；其他落子完成当前回合并把行动权交给对手。随后执行第 7.3 节的触发判定。

任一步失败都必须回滚整个试探事务。失败请求不产生捕获、不消耗配额、不增加动作数、不产生规则事件、不修改停着数或历史。

### 8.2 停着事务 — FROZEN

`PASS` 的提交过程为：

1. 验证阶段、行动者及续着限制；
2. 不改变棋盘，不执行捕获，不进行 PSK 拒绝检查；
3. 将 `A` 增加 1，增加连续停着数，提交动作事件；
4. 把未改变的稳定黑白占用作为一条新的、允许重复的历史记录追加；
5. 若为 `DOUBLE_START` 续着则解除续着义务；无论普通停着还是续着停着，回合完成后由对手接手；
6. 在 `COLLAPSE_PLAY` 中执行第 7.3 节触发判定；在 `ORDINARY_PLAY` 中执行第 11 节终局判定。

停着免于 PSK 拒绝，但不免于动作计数和事件记录。

## 9. 位置超级劫与历史

### 9.1 PSK 投影 — FROZEN

在一盘固定尺寸的对局内，PSK 键只比较每个固定坐标的三值占用：黑、白或空。坐标必须原样比较，不使用旋转、镜像或颜色交换等对称归一化。

PSK 键明确排除：

- 当前或下一行动者；
- `DOUBLE_START` 续着义务；
- 不灭、连着下、八方标记和锚点类型；
- 能力是否仍活着；
- 剩余配额；
- 全局动作编号；
- 连续停着数；
- 当前阶段；
- 事件 ID、时间戳和结算进度；
- 捕获计数及其他非占用元数据。

同一黑白占用即使具有不同标记、配额、行动者或阶段，也属于同一个 PSK 位置。

### 9.2 初始空盘与事件后追加 — FROZEN

- 初始空盘在第一个规则事件前作为 PSK 历史第零项播种；其索引固定为 `0`；
- 每个动作事件完成后的稳定占用都必须追加，包括停着造成的重复；
- 每个结算步骤事件完成能力停用、全盘重建、提子和确定性闭包后的稳定占用都必须追加，包括已捕获事件或已消耗 `DOUBLE_START` 事件形成的无操作重复；
- 任何具有稳定后状态的终局规则事件都必须追加该稳定占用；若某类终局记录被定义为不产生稳定后状态，则不得凭空伪造盘面事件；
- 试探性落子、重建过程、提子批次尚未完成时的盘面及结算闭包的不稳定中间盘面都不得追加；
- 历史有序且允许重复，不能用一个去重集合替代权威日志。实现可另维护集合以加速成员查询，但必须保留完整事件顺序和重复记录。

### 9.3 拒绝规则 — FROZEN

- 每个玩家落子在提交前检查候选占用是否已出现；出现即非法；
- `PASS` 不因重复被拒绝；
- 结算生成的盘面不因重复被拒绝；
- 结算重复、停着重复一旦进入历史，都会约束未来玩家落子；
- 结算前的完整历史在结算期间和结算后永久保留；结算步骤产生的历史也在之后永久保留。

结算绝不能因为 PSK 而中断、跳过移除、回滚触发动作或改变事件逆序。

## 10. 坍缩结算

### 10.1 入口 — FROZEN

结算在第 7.3 节触发动作已经完整提交后开始，且整盘只执行一次。入口操作为：

1. 保存第 7.4 节确定的 `handoffActor`；
2. 进入 `SETTLEMENT`，拒绝一切玩家动作；
3. 将连续停着数重置为 0；
4. 使所有未使用特殊配额失效，不给予补偿；
5. 收集双方全部已用特殊事件，包括棋子已被提走的事件和能力已消耗的 `DOUBLE_START` 事件；
6. 按其起源动作事件的唯一确定顺序，从最新到最旧排序。

若双方从未使用特殊能力，队列为空；触发动作的稳定占用已在历史中，结算可直接完成，不伪造特殊事件。

### 10.2 每个特殊事件的处理 — FROZEN

对排序队列中的每个事件 `e`，严格逐个执行。结算处理的是能力按全局最新到最旧顺序逐项停用，不是撤销动作：它绝不回滚已提交的落子、捕获、配额消耗、动作计数或事件。若对应棋子在该步骤开始时仍在盘上，它留在当前交叉点并转为普通棋子，除非随后在本步骤的确定性闭包中按规则被提走；若它早已被提走，结算不会使其复活。

```text
deactivate exactly e

repeat:
    rebuild every group, liberty set, and protection status on the whole board
    doomed = union of every group of either color
             whose liberty set is empty and which is not protected
    if doomed is empty:
        break
    remove all stones in doomed simultaneously

rebuild the whole board once more
emit one settlement-step trace referencing e and all removal batches
append the resulting stable occupancy to PSK history
continue with the next older special event
```

“失效”按类型解释：

- `IMMORTAL`：取消该事件的不灭保护；对应棋子若仍在盘上，先成为普通棋子；
- `EIGHTWAY`：取消该事件的 `N8` 接口；对应棋子若仍在盘上，先改用 `N4`；
- `DOUBLE_START`：机械能力早已消耗，本步骤只把账本事件标记为已结算，盘面是无操作；
- 对应棋子已不存在：盘面是无操作，但事件仍必须保留其顺序、轨迹和历史追加。

每一轮 `doomed` 必须包含两种颜色的所有零气不受保护棋块，并同时移除。闭包循环是规范要求，即使某个具体实现能够证明某些局面只需一轮，也不得以不同的顺序语义替代它。

一个较新的事件失效后，其闭包可能移除承载较旧特殊事件的棋子。轮到该较旧事件时，它仍产生一个可审计的无操作步骤和稳定历史记录。

### 10.3 结算出口 — FROZEN

全部事件处理完毕后：

- 所有特殊能力均永久失效；
- 未被移除的特殊棋子均按普通棋子参与后续围棋；
- 历史账本继续保留其特殊起源；
- 连续停着数为 0；
- 阶段变为 `ORDINARY_PLAY`；
- 当前行动者为入口保存的 `handoffActor`；
- 后续不得再次触发结算。

### 10.4 搜索原子性与完整轨迹 — FROZEN

对搜索而言，整个 `SETTLEMENT` 是一个不可打断的确定性状态转换：搜索树中不存在玩家在两个结算事件之间行动、选择移除顺序或停止闭包的节点。

对权威事件日志、回放和 UI 而言，必须保留完整的最新到最旧事件顺序、每个事件的失效、每批同时移除以及每个事件闭包后的稳定占用。即使搜索只暴露结算前和结算后决策状态，其搜索状态仍必须包含结算步骤逐项加入后的完整 PSK 历史。

## 11. 结算后普通围棋、终局与计分

### 11.1 普通行棋 — FROZEN

结算完成后：

- 只允许 `NORMAL` 落子和 `PASS`；
- 所有棋子使用 `N4` 接口，因为不存在活八方锚点；
- 不存在不灭保护；
- 第 8.1 节事务因此退化为标准的“先提对手、禁止本方无气自杀、再检查 PSK”的普通围棋落子；
- 完整 PSK 历史继续生效；
- 全局动作计数继续增加，但不再检查坍缩阈值。

### 11.2 两次新的停着 — FROZEN

结算入口已把此前停着清零。因此，双方必须在 `ORDINARY_PLAY` 中重新形成两个连续 `PASS` 才能结束普通行棋。任何中间落子都把连续停着数清零。

阈值前触发结算的两次停着不能同时作为整盘终局停着；动作 `T` 前后形成的旧停着也不能跨越结算沿用。

### 11.3 MVP 死子处理 — 捷径 DEFERRED；确定性路径 FROZEN

MVP 不启用“双方同意同一死子集合后直接移除”的捷径，也不启用死子提案、争议、恢复行动者或恢复 `PASS` 连计的协商协议。两次 `PASS` 后，规则直接对当前稳定盘面执行第 11.4 节的中国式面积计分；不会额外移除棋子，也不会因历史提子或假定死子增加分数。

若玩家认为盘上仍有必须处理的棋子，应在提交终局的两个连续 `PASS` 之前继续实际 `ORDINARY_PLAY`。未来版本可以另行设计双方一致移除与争议恢复协议，但启用该捷径必须经过新的语义版本、描述符和协议测试；不得把未来设计回填为当前 MVP 行为。

### 11.4 中国式面积计分 — FROZEN

在用于计分的最终盘面上，先按 `N4` 将所有空点划分为空区域。一个空区域：

- 只邻接黑子且不邻接白子，则全部计为黑方空地；
- 只邻接白子且不邻接黑子，则全部计为白方空地；
- 同时邻接双方，或不邻接任何一方，则不计给任何一方。

设：

- `stonesBlack`、`stonesWhite` 为盘上黑白棋子数；
- `areaBlack`、`areaWhite` 为上述各方空地点数。

则：

\[
S_B=stonesBlack+areaBlack,
\]

\[
S_W=stonesWhite+areaWhite+7.5.
\]

以 `S_B-S_W` 判定胜负和目差。历史提子数不另行计分；当前 MVP 不存在协商死子移除。特殊棋子的历史种类和标记不改变每枚盘上棋子的一点面积价值。

### 11.5 认输与超时 — FROZEN

认输和游戏语义超时是管理终止候选，只能在对外暴露的稳定命令/决策边界接受：`COLLAPSE_PLAY`（包括存在 `pendingDouble` 的续着决策边界）或 `ORDINARY_PLAY`。

- 若 C++ 权威顺序在某候选原子动作提交之前接受管理终止，则相关玩家立即负、对手立即胜；该候选动作不得提交，不执行坍缩结算、死子协商或面积计分，也不增加原子动作数。
- 认输或超时提交一个具有稳定后状态的终局事件；棋盘、棋子来源、配额、账本、动作计数、停着计数、pending Double 与 settlement 完成事实保持不变，终局状态、修订、日志位置和 PSK 历史按终局事件更新。未改变的稳定占据作为新的历史条目追加。
- 原子动作一旦提交，若它触发 settlement，则该动作和完整 settlement 闭包必须作为一个不可打断的语义事务运行到出口。settlement 从入口到出口不暴露认输、超时、取消或其他命令边界；稍后到达的管理终止只能在完整 `ORDINARY_PLAY` 稳定状态暴露后再处理。

请求超时、传输超时、背压、断线或取消不是游戏语义 `TIMEOUT`，不得自动生成胜负。时间控制参数、时钟同步和超时证据协议属于 **UNFROZEN**。

## 12. 权威边界、记录与公开身份

### 12.1 实现权威边界 — FROZEN

- **C++**：唯一生产规则与搜索权威，负责合法性、捕获、PSK、当前行动者、续着义务、结算、终局和计分。
- **Python**：独立实现的慢速参考和差分预言机；不得只是调用或包装 C++ 规则逻辑后宣称独立一致性。
- **Node gateway**：仅负责进程、会话、WebSocket 和 Schema 编排，不自行修复、补算或裁决规则状态。
- **React + TypeScript client**：只渲染权威状态；不得计算合法性、捕获、劫、计分、结算、当前行动者或终局。

### 12.2 权威记录 — FROZEN

经验证的 JSON 事件日志是单盘对局的权威记录。给定同一规则身份、初始状态和事件日志，规则归约必须重放出相同的：

- 每个动作稳定状态；
- `DOUBLE_START` 续着状态；
- 完整 PSK 历史；
- 结算事件逆序和闭包轨迹；
- 当前行动者；
- 终局与计分结果。

扩展 SGF 仅用于交换和展示，不是权威记录；它不得在与 JSON 日志冲突时覆盖 JSON，也不能因为无法表达续着、标记或结算轨迹而让客户端自行猜测。M0 Action/描述符/投影/夹具 Schema 已冻结；其外的生产 JSON 事件字段和扩展 SGF 属性仍为 **UNFROZEN**。

C++ 是生产语义归约器的权威，JSON 是一盘游戏已经发生事件的权威记录；二者职责不同，不构成冲突。无效或被篡改的 JSON 不能凌驾于规则合法性验证。

### 12.3 公开不可变规则身份 — FROZEN

公开规则身份三元组固定为：

```text
rulesetId:       mutago.collapse-go
semanticVersion: 0.1.0-draft
descriptorSha256: a21c67d7962b71a3a53b895de824dc6312502362de5341103c0265c2c81d0899
```

摘要输入是 [`rulesets/collapse-go/descriptor-v0.1.0-draft.json`](../../rulesets/collapse-go/descriptor-v0.1.0-draft.json) 通过 profile `rfc8785-jcs-ascii-safe-integer-v1` 产生的 14973 个规范 UTF-8 字节。该 profile 以 RFC 8785/JCS 为基础，只约束 JSON 词法、值域和规范字节：有效 UTF-8、无重复键、ASCII 字符串与对象键、安全有符号整数 `[-9007199254740991,9007199254740991]`、布尔、`null`、数组和对象；对象键按 UTF-16 code unit 字典序排列。浮点数、非 ASCII 数据和 unsafe integer 由 profile 拒绝。规则描述符还必须独立通过关闭式 `ruleset-descriptor-v1` Schema、描述符跨字段不变量和适用的跨制品绑定；未知描述符字段与不满足 Schema 的值由该验证层拒绝，而不是由 canonicalization/hash 层拒绝。摘要算法固定为 SHA-256，公开编码固定为 64 个字符的 lowercase hexadecimal。

内部 variant 枚举、`collapse-go` 目录 slug、运行模式标签、Git 提交 SHA、构建产物 SHA 和模型 SHA 均与公开身份分离，不能作为 `rulesetId`、语义版本或描述符摘要的别名。独立 C++ 与 Python 实现必须从同一原始 JSON 按上述 profile 得到逐字节相同的规范结果；M0 的 Python 合同工具和中立向量只是可执行合同，不是生产规则权威或完整 Python 规则 oracle。

该描述符完整绑定官方 19×19 空盘、黑先、双方 `1/1/1` 配额、阈值与居中政策、固定 1445 动作空间、初始空盘 PSK 第零项、三种能力、动作与事件边界、settlement、PASS、MVP 禁用死子协商移除与争议协议、计分和终局。任何改变这些语义的后续规则必须使用新的 `semanticVersion` 和新的规范描述符摘要。

### 12.4 四类键必须分域 — FROZEN

| 域 | 语义 | 不得替代 |
|---|---|---|
| 公开规则身份 | 标识一套不可变规则语义 | 任何局面键 |
| PSK 键 | 仅当前黑白占用，用于重复判定 | 搜索键、NN 缓存键 |
| 搜索/置换键 | 必须区分所有会影响未来合法性或结果的状态，如行动者、阶段、续着、配额、活能力、动作计数、停着和 PSK 历史 | PSK 键、NN 缓存键 |
| NN 缓存键 | 标识确定的网络、输入特征和推理配置 | PSK 键、搜索键 |

PSK 的语义投影已经 **FROZEN** 为仅黑白占用；只有其字节序列化、哈希实现、碰撞处理和存储布局仍为 **UNFROZEN**。`SearchKey` 与 `NNCacheKey` 的必需语义字段已经由 [`04-输入特征ABI-V9.md`](04-输入特征ABI-V9.md) §G.3–G.4 冻结；Model V19 与 Inputs V9 同样为 **FROZEN DESIGN / NOT YET IMPLEMENTED**。仍为 **UNFROZEN** 或 **AUDIT-BLOCKED** 的仅是物理字节编码、digest/hash 与碰撞实现、缓存层级选择、淘汰/生命周期、存储布局和上游集成。四域不得因“当前碰巧相同”而复用同一个语义键。

### 12.5 固定 ABI 与上游基线 — FROZEN

本规则文档绑定的仓库/上游基线仅为 KataGo stable v1.16.5，提交 `ba938676d7f42d70950b3a535af2466fb642008c`。关联兼容性版本为 **MutaGo Model V19、Inputs V9、Training Schema V1、Action Schema V1**；动作编码以第 3.9 节和 [`04-输入特征ABI-V9.md`](04-输入特征ABI-V9.md) 为准。

固定基线的仓库内说明见 [`docs/upstream/KataGo-README-v1.16.5.md`](../upstream/KataGo-README-v1.16.5.md)。这些版本绑定与公开规则身份属于不同域，不得用模型、构建产物或上游提交哈希替代 `mutago.collapse-go` 的描述符身份。

## 13. 规范不变量

以下不变量均为 **FROZEN**：

1. **单点占用**：每个交叉点恰为黑、白、空之一。
2. **动态重建**：棋块、气和保护只由当前盘面及仍活着的能力决定。
3. **连接对称**：同色连接按“任一端点暴露接口”形成无向边。
4. **气去重**：一个空点对同一棋块最多贡献一口气；占用点永不贡献气。
5. **稳定零气**：稳定状态中的每个零气棋块都含活不灭锚点。
6. **动作单调**：`A` 恰等于已提交落子和停着总数，只增不减；结算不增加 `A`。
7. **事件对应**：每个原子动作恰有一个动作事件；每个已用特殊事件恰有一个按全局逆序处理的结算步骤。
8. **配额单调**：特殊配额只会因合法提交减少，绝不因捕获返还；结算后全部为零或失效。
9. **续着完整**：非终局状态下，`DOUBLE_START` 起始动作之后只能由同一玩家提交一个 `NORMAL` 或 `PASS`；之后才轮到对手。
10. **阶段排他**：结算期间没有玩家动作；结算后没有特殊动作；结算只发生一次。
11. **PSK 纯占用**：PSK 判等不包含任何非黑白占用字段。
12. **初始与事件后历史追加**：初始空盘占据是 PSK 历史第零项；此后每个具有稳定后状态的规则事件都按顺序保留其稳定占据。停着、无操作结算和其他生成的重复不得被删除，不稳定中间盘面不得加入。
13. **玩家落子不重复**：任何已提交玩家落子产生的占用在提交前都不曾出现；停着和结算不受此拒绝规则约束。
14. **结算确定性**：同一入口状态和同一事件账本必得同一逆序、移除批次、历史和出口状态。
15. **结算原子性**：从触发原子动作提交点开始，直到全部结算步骤、PSK 追加、出口行动者/阶段和最终修订共同提交完成，玩家、搜索、认输、超时、取消和其他命令都不能介入；禁止范围包括第一个结算步骤之前、任意两个步骤之间以及最后一个步骤到出口提交之间。
16. **交接保持**：结算出口行动者等于触发回合正常结束后本应行动的对手。
17. **结算后普通化**：仍在盘上的特殊棋子只按普通棋子参与连接、捕获和计分。
18. **权威归约**：客户端和网关不能成为规则计算来源。
19. **身份分域**：公开身份、PSK、搜索和 NN 缓存键互不混用。

## 14. 有限性与终止

### 14.1 坍缩前阶段必然有限 — FROZEN

`COLLAPSE_PLAY` 最迟在第 `T` 个原子动作后进入结算；阈值前双停着只会使它更早结束。`DOUBLE_START` 起始编号上限保证不会遗留未完成续着。

### 14.2 每次结算必然有限 — FROZEN

- 已用特殊事件数有限；官方配置最多为双方各三次，共六个事件；
- 每个事件只失效一次；
- 闭包每次非空移除至少一枚棋子，棋盘最多有 `N²` 枚棋子；
- 事件失效不可逆，闭包只移除、不新增棋子。

因此结算总会在有限步骤内结束。

### 14.3 结算后 MVP 规范路径 — FROZEN

MVP 固定采用“两次停着后按当前稳定盘面直接计分”的确定性路径，因此结算后行棋有限：PSK 使每个合法落子产生此前未出现的黑白占据，而固定棋盘只有有限个占据；合法落子最终耗尽，此后只能停着，并由两个连续停着终局。

### 14.4 未来人类协商扩展 — UNFROZEN / DEFERRED

双方一致移除死子、分歧后恢复行棋以及相关协议活性不属于 MVP。若未来版本启用这些能力，必须另行冻结动作边界、恢复行动者、`PASS` 状态、提案轮次、超时与收敛策略，并分配新的语义版本和描述符摘要。

## 15. 规范示例与边界情形

以下示例均为 **FROZEN** 语义；坐标只用于说明，不固定未来协议的坐标编码。

### 15.1 阈值边界与连着下

在 19×19：

- 当 `A=148` 时，下一动作编号为 149，可以使用 `DOUBLE_START`；
- 起始落子提交后 `A=149`，同一玩家必须续着；
- 续着作为动作 150 完整提交并成为结算前最新动作事件；
- 随后立即结算，出口行动者是该玩家的对手；
- 当下一动作编号已经是 150 时，请求新的 `DOUBLE_START` 非法；
- 同一动作 150 使用 `IMMORTAL` 或 `EIGHTWAY` 可以合法，且若提交成功，该特殊事件在结算中最先失效。

### 15.2 阈值前双停着不是终局

若动作 40 和 41 是相邻的两个 `PASS`：

- 动作 41 提交并追加重复占用；
- 因 `41<T(19)`，立即进入结算；
- 不进行面积计分；
- 结算出口停着数为 0；
- 结算后双方还需重新连续停着两次才能终局。

若 `DOUBLE_START` 起始落子后续着为 `PASS`，起始落子已把停着数清零，所以该续着只是第一手停着；对手随后 `PASS` 可以成为第二手并在阈值前触发结算。

### 15.3 不灭零气和真眼侵入

黑方把 `IMMORTAL` 落入一个普通意义上的白方真眼。若落子后的黑棋块没有气，但包含刚落下的活不灭锚点：

- 黑棋块受保护，不因零气自杀而非法；
- 白方棋块仍按其实际气和保护判定；
- 普通“两眼必活”结论不能移除黑不灭子；
- 黑方以后可以通过合法动作继续侵入或填充，从而破坏白方普通两眼结构；
- 若该占用违反 PSK，落子仍然非法，不灭不豁免 PSK。

### 15.4 八方肩点不切断

黑方活八方锚点位于 `(4,4)`，普通黑子位于 `(5,5)`。即使 `(5,4)` 与 `(4,5)` 被白子占据，两枚黑子仍通过八方锚点的直接对角接口连接。两个肩点不是连接路径，不具有“切断”权。

若某空点同时被八方锚点和同块其他棋子的接口触及，该空点仍只贡献一口气。

### 15.5 失去八方连接后的保护分裂

一个黑棋块通过活八方锚点的对角边连接成两部分，其中只有左侧部分另含活不灭锚点。八方事件失效后：

1. 全盘改用剩余活能力重建；
2. 对角连接消失，原棋块分裂；
3. 左侧碎片因含活不灭锚点继续受保护；
4. 右侧碎片不继承历史保护；若零气，则在当前结算闭包中被移除。

### 15.6 同时捕获与本方检查顺序

一次落子同时使多个不受保护的对手棋块零气。所有这些对手棋块必须基于同一次第一次重建一起进入待移除集合并同时移除。移除后再重建，最后检查新落棋子所在本方棋块。实现不得先移除一个对手棋块、重建后再决定另一个棋块是否被提。

### 15.7 PSK 排除元数据

假设历史中已有某个黑白占用 `X`。当前局面在行动者、配额、特殊标记或阶段上与历史记录不同，但某个候选落子仍会产生占用 `X`。该落子必须因 PSK 非法，因为这些元数据不属于 PSK 键。

一个 `PASS` 留下占用 `X` 可以提交并追加重复记录；一个结算无操作步骤留下 `X` 也可以提交并追加。此后任何玩家落子若产生 `X`，仍被拒绝。

### 15.8 跨双方的最新优先结算

设已用特殊事件按时间从旧到新为：

1. 黑方不灭 `e12`；
2. 白方八方 `e27`，其棋子后来已被提走；
3. 黑方连着下 `e35`，能力已在起始动作时消耗。

结算顺序必须是 `e35 → e27 → e12`：

- `e35` 是连着下无操作步骤，仍追加稳定占用；
- `e27` 因锚点已不存在也是无操作步骤，仍追加稳定占用；
- `e12` 最后失去不灭保护，重建并执行闭包。

不得删除两个无操作事件后直接处理 `e12`。

### 15.9 动作 T 的特殊事件先提交后撤销

在动作 150 放置不灭棋子时，先完整执行统一落子事务。不灭可以使其新棋块在零气下合法存活，动作事件和占用进入历史。随后结算开始；因为它是最新已用特殊事件，其保护首先失效，结算闭包可能立即移除该棋块。该结果不是回滚动作 150，而是动作提交后发生的确定性结算。

### 15.10 捕获不返还、未用不补偿

八方棋子在结算前被提走：其玩家不能再次使用八方，事件仍进入结算。另一位玩家若从未使用不灭，提前双停着触发结算时，该未用配额直接失效，不增加面积分或行动次数。

### 15.11 面积计分示例

若最终盘面黑方棋子与黑空地合计 180 点，白方棋子与白空地合计 181 点，则：

- 黑方 `S_B=180`；
- 白方 `S_W=181+7.5=188.5`；
- 白胜 8.5 点。

此前双方各提过多少子不另行加入分数。

### 15.12 认输与超时

若动作 100 后的稳定决策边界某方认输，或在 `DOUBLE_START` 续着尚未提交的暴露边界发生有效游戏超时，对手立即胜，不启动结算或计算盘面分数。若某原子动作或续着已经先提交并触发结算，则完整结算先运行到出口；settlement 内部不存在插入认输、超时或取消的边界。

## English Summary

Collapse Go `0.1.0-draft` has frozen gameplay semantics despite the word “draft.” The official game is even play on an empty 19×19 board, Black first, with White komi 7.5, Chinese area scoring, and occupancy-only positional superko. The pinned upstream baseline is KataGo stable v1.16.5 at `ba938676d7f42d70950b3a535af2466fb642008c`. The associated compatibility stack is MutaGo Model V19, Inputs V9, Training Schema V1, and Action Schema V1.

Before the one-time settlement, each player has one Immortal, one Double-Move, and one Eightway ability. The threshold is `T(N)=floor((150N^2+180)/361)`, giving 34, 70, and 150 actions on 9×9, 13×13, and 19×19. Settlement starts after action `T`, or after two consecutive passes strictly before `T`. `DOUBLE_START` is legal only when `A+2<=T`; its mandatory continuation is a separate `NORMAL` or `PASS` action by the same player.

Action Schema V1 is kind-major: `a=361*k+p`, with NORMAL `0..360`, IMMORTAL `361..721`, DOUBLE_START `722..1082`, EIGHTWAY `1083..1443`, and PASS `1444`. Canonical Action V1 is a closed object containing exactly `schemaVersion`, `actionId`, and `kind`; coordinates are uniquely derived from `actionId`, and missing/unknown fields, unknown versions, redundant coordinates, and inconsistent `kind`/ID pairs fail closed. The 9x9, 13x13, and 19x19 footprints are centered on the 19x19 canvas at offsets `(5,5)`, `(3,3)`, and `(0,0)`, and point actions outside the active footprint are rejected.

Every placement uses one ordered transaction: tentative placement; mixed-connectivity rebuild; simultaneous removal of all zero-liberty unprotected opponent groups; rebuild; own-group survival check; occupancy-only PSK check; and atomic commit. Pass is exempt from PSK rejection but still appends its stable occupancy. Initial empty occupancy is the sole PSK history entry at initialization and has index zero. Every accepted action with a stable post-state appends that stable occupancy; every settlement-event closure does so as well, while unstable rebuild and capture intermediates never enter PSK history.

Settlement processes all used special events across both players from newest to oldest. It disables one event’s ability at a time, rebuilds the whole board, removes all zero-liberty unprotected groups of both colors simultaneously to deterministic closure, and appends the resulting stable occupancy. Settlement never rolls back placements, committed captures, quotas, action counts, or events. Captured special events and consumed Double-Move events remain ordered auditable no-op steps.

After settlement, all remaining stones are ordinary and only `NORMAL` and `PASS` are legal. Two new consecutive passes are required before scoring. The MVP enables neither an agreed dead-stone removal shortcut nor a dead-stone dispute protocol; ordinary play continues until two consecutive passes, then the current stable board is scored. Resignation or game timeout terminates immediately without settlement or scoring only when accepted at an exposed stable decision boundary before a candidate action commits. Once an atomic action commits, any settlement it triggers completes atomically and exposes no command boundary; a later administrative termination can be accepted only at the resulting post-settlement decision state. Operational timeouts and cancellation never synthesize game `TIMEOUT`. A future negotiation extension requires a new semantic version, descriptor, and protocol tests.

The frozen public identity is `rulesetId` `mutago.collapse-go`, semantic version `0.1.0-draft`, and descriptor SHA-256 `a21c67d7962b71a3a53b895de824dc6312502362de5341103c0265c2c81d0899`. The restricted `rfc8785-jcs-ascii-safe-integer-v1` profile governs JSON syntax, value domain, and canonical bytes only: valid UTF-8, duplicate-key rejection, ASCII strings/keys, safe signed integers, booleans, null, arrays, and objects, with floats, non-ASCII data, and unsafe integers rejected. The 14,973-byte canonical rules descriptor separately passes the closed descriptor schema, descriptor invariants, and cross-artifact bindings; unknown descriptor fields are rejected by that validation layer. `canonicalize`/`hash` enforce only the profile, while descriptor `validate` and repository `check` enforce Schema and applicable invariants. Internal variant enums, repository slugs, and runtime labels are not public identity. Any semantic change requires both a new semantic version and a new canonical descriptor hash. C++ is the sole production rules authority, Python is an independent reference oracle, JSON is the authoritative game record, and the Gateway and client must not compute rules.
